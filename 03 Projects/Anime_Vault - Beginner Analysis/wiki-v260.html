A local desktop manager for a personal anime collection spread across a dozen external drives. Written by mranex — the same author as the manga tool (v256), the light-novel workbench (v257) and the subtitle extractor (v258). This is the fourth repository in four consecutive ships, and the first test of the same-author control the operator ratified one ship ago.

It is the best-built of the four. It is also documented so that following its own instructions cannot make it run.

01Eighty-seven minutes, and the order matters

Two independent clones, diff -rq clean in both directions. One root commit, zero merges, zero tags, one branch. The entire repository history is three commits:

  1. 07:24Initial commit2 files · 222 insertions — .gitignore + LICENSE, and nothing else
  2. 08:43First Commit74 files · 20,744 insertions — the whole application, at once
  3. 08:51Readme.md1 file · 145 insertions

This repository was never the workspace. It is a destination for code that already existed on the author's machine. And the ignore rule — which names __pycache__/ three separate ways — was committed seventy-nine minutes before the first Python file.

A pack-level check (rev-list --objects --all) confirms the tree equals the history: nothing was ever added and later deleted. Hold on to both of those facts; section 04 is where they pay off.

02The manifest is the fossil

The README mentions FastAPI nine times and Tauri ten times. It mentions PyQt once, and app.py zero times. It declares the migration in plain language — “inherited and comprehensively upgraded from the antiquated PyQt6 version” — and gives three install commands:

pip install -r requirements.txt   README:94
npm install                       README:100
npm run tauri dev                 README:107

And requirements.txt, the only Python dependency declaration in the repository, is two lines:

PyQt6>=6.7,<7
pyinstaller>=6,<7
Finding

fastapi, pydantic and uvicorn — imported at server.py:10–12 and launched at :661 — appear in it zero times.

The README describes generation two nine times over, and the only machine-readable dependency declaration in the repository describes generation one: the generation the README itself calls antiquated. The install list is a fossil of the program the documentation was written to replace.

This is the fourth mechanism for one outcome across the four siblings — and under the control's own rule, an outcome reached through different mechanisms is stronger evidence than one that repeats identically.

Four repositories, four mechanisms, one outcome: in every one of this author's projects, the instructions for making the program run describe something other than the program. It is the strongest disposition in the set.

03Three ways to hide the same error

The documented app does not run the Python directly. The Rust shell spawns it — and the README explains this accurately, including the Windows flag that suppresses its console.

src-tauri/src/lib.rs
:42  let mut cmd = Command::new("python");
:46     cmd.arg("-m").arg("movie_vault.server")
:48        .arg("--host").arg("127.0.0.1")
:50        .arg("--port").arg("5000");
     // Prevent command prompt popups on Windows in both dev and production
:57     cmd.creation_flags(0x08000000); // CREATE_NO_WINDOW
:60  match cmd.spawn() {
        Ok(child) => { println!("Successfully launched Python API server"); … }

The port matches — the frontend hardcodes 127.0.0.1:5000 in twenty-three places and the server defaults to it. But three independent mechanisms each turn a loud failure into a silent one:

  • spawn() answers the wrong question. It returns Ok when the binary launches, and knows nothing about the ImportError that follows.
  • The success message is printed on the strength of that spawn, not of a running server.
  • CREATE_NO_WINDOW deliberately removes the channel the traceback would have used — “in both dev and production.”
And the install path guarantees it

pip install -r requirements.txt installs neither FastAPI nor uvicorn nor pydantic. The app opens, renders, prints “Successfully launched Python API server”, and all twenty-three of its API calls fail — with the cause suppressed by design on Windows.

The README documents the mechanism that conceals its own defect, in prose, as a feature.

The rule: spawn() tells you a process started, not that it is running. A success message printed on a spawn is a false success — the same class as an exporter exiting zero while the original bytes survive, now at N=2 in the corpus by a different mechanism.

Read-derived, not executed: Python is unavailable in this sandbox and there is no Windows host. The chain is legible from the quoted code. In tauri dev on a Unix host the traceback would reach the console; in a packaged Windows build, per line 57, it would not.

The confound

Committed bytecode, committed machine paths and dead generations all accumulate over time in the directory you work in. The other three repositories ran 31 days, 14 days and 2.4 days inside their repos. This one was a bulk import: git init → .gitignore → push produces a clean tree with no change in behaviour whatsoever. The sixth habit breaks for the same structural reason — the README was written eight minutes after the code landed, as an install sheet, with no room for a performance claim.

The control must record, per repository, whether the repository was the workspace or a destination. Habits that accumulate in a working directory are unobservable in a bulk import, and reading their absence as discipline mistakes workflow for character.

At v257 I wrote, in bold: “Not a learning curve. Two projects side by side, one tended and one not.” That was the right read of two data points. At four, with creation dates visible, the bookkeeping outcomes do improve from first-created to last — but not monotonically, and the improvement has a mechanical explanation requiring no learning at all.

The honest statement: neither a learning curve nor mere inattention — a workflow difference that mimics both. What survives the control are exactly the two habits independent of where the code was written: the run-instructions defect, and the total absence of any verification. Those two are properties of the author. The other four were properties of the directory.

05What he got right, and it is more than the others

The previous ship's best finding was that code moves forward in time and never backward: a guard invented in v256 reached v258 eleven days later and never reached v257, because copy-forward is a one-way ratchet. Only a shared library makes a fix travel back.

This repository is the same author solving that problem, correctly, inside one project.

movie_vault/core/          ← one shared layer
  db.py             2,134 lines
  randomizer.py       187
  scanner.py          195   backup.py 170   hdd_identifier.py 297   paths.py 104

three front ends over it:
  app.py                 a CLI
  movie_vault/ui/*.py    the PyQt GUI — 6 modules, all importing core.*
  movie_vault/server.py  a FastAPI API → React → Tauri
The ratchet, defeated

server.py:14 carries the comment # Import existing core modules — the author writing down, in the file that bridges old to new, that he is reusing rather than reimplementing.

And the load-bearing function is genuinely shared: pick_random_item, the app's entire point, lives once in core/randomizer.py:64 and is called by both UIs — ui/random_page.py:37 and server.py:35. A fix to the picker reaches the desktop app and the web app at the same moment.

But the sharing leaks, and the leak is the more useful half. Two sites were reimplemented in TypeScript rather than called over the API — Library.tsx:144 and RandomPicker.tsx:144 — both using sort(() => Math.random() - 0.5), the classic biased comparator shuffle that is not a uniform permutation. In fairness the primary pick is unaffected: RandomPicker.tsx:156 fetches /api/random/pick, which calls the shared implementation. The biased shuffles govern a browse pool and a cosmetic tarot deck.

Extracting a shared core makes fixes travel; it does not stop a new front end from re-implementing what it could have called. The ratchet is defeated by architecture and re-created by convenience — 187 correct lines sat one HTTP call away from two incorrect ones.

The rest of the credit, briefly

  • Clean SQL across a 2,134-line data layer: 68 execute( calls, zero f-string SQL, zero %-format, 85 placeholders.
  • Zero shell=True in twenty Python files. The v257 sibling had two, in the program its README told you to launch.
  • The only bounded dependency pins of the four — both with upper bounds. The best-formed manifest in the set, describing the wrong program.
  • A real Apache-2.0 file in the first commit: the clearest grant of the four, against one AGPL file added last, one licence asserted only in prose, and one repository granting nothing at all.
  • The claimed features exist. The randomiser takes fourteen parameters, and the README's “anti-repeat algorithm” is real — avoid_recent_limit=20, with a fallback_used field so the caller knows when the filter had to relax.

06Defects beyond the headline

Wildcard CORS, no authentication

server.py:46–49 sets allow_origins=["*"] with credentials and all methods, and the file has zero occurrences of Depends, api_key, token or Authorization. It binds to loopback, which limits the blast radius — but while the app runs, any web page open in any browser on that machine can reach an API that scans the filesystem and writes to a database. Third broken-auth-shaped defect in this set of four.

  • Silent degradation on a missing stylesheet — main_window.py:195–199 returns quietly if the .qss is absent, and the app runs unstyled with no warning. Structurally identical to the v257 sibling rendering a prompt with no JSON contract for the same reason. N=2 in the set.
  • Zero tests of 76 files; zero CI on any ref, ever. Nothing here can notice anything above — and the manifest divergence in particular is one grep away from impossible.
  • A live generation the README calls antiquated and never addresses. The PyQt UI is roughly 130 KB of shipped, reachable code. This is not the v257 defect: the migration is declared. It is the honest twin — the old generation is present, acknowledged as the predecessor, and simply never mentioned as a thing still in the tree.

07Verdict, and the one thing worth ninety minutes

No mint. Domain-not-capability is decisive, and sharing a core across a CLI, a GUI and an HTTP API is standard layered architecture older than anything in this corpus. Counts unchanged at 46 patterns and 12 confirmed vocabulary items.

Goal-relevance, stated bluntly. Zero LLM, zero agent surface, zero CI — the one hit from an eight-term AI grep across the whole tree was ScrollMode matching llm. On its own domain this subject does not clear the bar, and off-goal capture is recorded as the strongest such alternative of the four siblings. It lands goal-aligned on two things only: it is the instance that found the control's confound, and its architecture answers a decision the last audit left open. The off-goal election would cost nothing — the rolling ceiling stays clear either way.

Pilot — read and re-derive; install nothing

Ninety minutes: settle the shared-owner question the audit left open. Name one owner per fact, make the routine deltas reference rather than restate, and where sharing is genuinely impossible, declare which copy wins inside the copy that loses. Then add the check — because this repository is the proof that the invariant will not be maintained by hand.

Twenty minutes: one CI clause worth having anyway — every third-party module imported by an entry point must appear in the manifest the README tells you to install. And anywhere a subprocess, worker or container is launched, log success from a readiness probe, never from a spawn.
