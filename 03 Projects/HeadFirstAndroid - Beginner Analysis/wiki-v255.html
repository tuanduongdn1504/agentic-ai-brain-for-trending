Four Edits,
Nine Years

The companion code to a 2015 Android textbook has not changed a byte since May 2017. Its curriculum is still coherent, its links still resolve, its images still load. Measured against its own claims it is more faithful than any subject this corpus has examined in five ships — and it is nearly unusable, because the world moved out from under it.

B
Why it broke

JCenter's death was selective

All 28 build.gradle files declare exactly one repository — jcenter() — and none declares google(). JCenter now redirects to Maven Central, so the error message points the developer at a repository that answers HTTP 200. They follow it, find a healthy live service, and start debugging the wrong thing.

But the redirect works fine for everything with a second home. I watched the repaired build pull jacoco, ASM, ProGuard, protobuf and kotlin-stdlib straight through jcenter.bintray.com, because all of them are also on Maven Central. And Google still serves every 2015-era support library this repo asks for.

The asymmetry

Also 404 on maven.google.com, repo.maven.apache.org and plugins.gradle.org/m2. Google moved the Android Gradle Plugin to its own repository at 3.0 and never republished 2.x. Google still serves the 2015 libraries and has dropped the 2017 plugin that consumes them — so the one artifact with no second home is the one that assembles all the others.

Correction to my own hypothesis

I predicted the fix was a single google() line. I tested it. The build failed identically, because AGP 2.3.2 is not there either. The plugin has to be upgraded, which drags Gradle with it — hence three edits, not one.

C
The ninth app

An issue opened in April 2017, reproduced this afternoon

Eight of nine apps run correctly on Android 15. The ninth is Odometer, the only one of the fourteen that requests a permission.

java.lang.RuntimeException: Unable to create service com.hfad.odometer.OdometerService: java.lang.SecurityException: uid 10214 does not have android.permission.ACCESS_COARSE_LOCATION or android.permission.ACCESS_FINE_LOCATION. at android.location.LocationManager.requestLocationUpdates(LocationManager.java:1212) at com.hfad.odometer.OdometerService.onCreate(OdometerService.java:54)

OdometerService.java:54 calls requestLocationUpdates in onCreate(). A grep across both of the app's Java files for checkSelfPermission or requestPermissions returns zero. The code uses the pre-Marshmallow install-time permission model — correct for targetSdkVersion 21, wrong for anything at or above 23.

Issue #25 · opened 2017-04-05 · zero comments · still open

“It appears as if the code isn't working in Chapter 13 because when using a dangerous service you explicitly need to ask for permissions from the user.”

DuaneQ was right. Nine years, four months and fifteen days later I reproduced his crash with the exact stack trace he predicted, and nobody has ever replied to him. 313 people have forked this repository, and every one of them who reaches chapter 13 hits the same wall.

E
Two silent successes

The tests are green. The notification is gone.

Fourteen files named ApplicationTest.java, all exactly twelve lines, zero test methods, zero assertions. So far, unremarkable — until you run them.

$ ./gradlew connectedCheck :app:connectedCheck BUILD SUCCESSFUL in 4s <testsuite name="com.hfad.myfirstapp.ApplicationTest" tests="1" failures="0" errors="0" skipped="0"> <testcase name="testApplicationTestCaseSetUpProperly" /> </testsuite>

The author wrote no test methods. The deprecated JUnit3 base class supplies one, and it asserts that the test harness set itself up. It tests the framework, not the application. Any metric that counts test files, test results, or CI green reports this repository as tested.

And the one real test in the repository — a 65-line Espresso test with a twenty-line Javadoc patiently explaining what an instrumented test is — sits on the secondEdition branch, never merged. It is the best-taught file here.

Then push targetSdkVersion to 26, which Google Play now requires at 36:

E NotificationService: No Channel found for pkg=com.hfad.joke, channelId=null, id=5453 notification=Notification(channel=null … defaults=VIBRATE flags=AUTO_CANCEL) # no crash. no FATAL EXCEPTION. no notification. nothing in dumpsys.

The user presses “WHAT IS THE SECRET OF COMEDY?”, waits the service's ten seconds, and nothing happens — forever, with one line in a log nobody reads. A fleet agent claimed this crashes with an IllegalArgumentException. It does not; I ran it.

Notification channels became mandatory in Android 8.0, three months after the last commit to this branch. The usable window is exactly targetSdk 24–25: the OS refuses to install below 24, and this code fails silently at 26.

F
Stale and correct

The label that is wrong on purpose

The README maps chapter 7 to chap10img.png, chapter 11 to chap07img.png, and so on for seven consecutive chapters. It reads as an off-by-N bug.

I opened the images. chap10img.png shows the Workout app's two fragments side by side on a tablet — chapter 7's content. chap07img.png shows Starbuzz with a SQLite helper — chapter 11's content. The mapping is correct. The filenames are relics of a pre-publication chapter numbering, and the README compensates at the reference site.

Where the obvious fix is the bug

An agent asked to “fix the mismatched image references” would renumber them to match the filenames and silently break every picture in the README.

This is the vault's own disease, solved the other way. At v245 this corpus adopted a rule from unslothai/unsloth: when two documents must carry the same fact and mechanising it is impractical, declare which copy wins, inside the copy that loses. It applied that to a chapter file whose filename has been wrong for 71 ships. The drift stayed; the declaration made it harmless and self-diagnosing.

Griffiths reached the same correctness without the declaration. Nothing anywhere says the filenames use the old numbering. It is correct today and fragile forever.

The rule

A stale label is safe when it is declared and dangerous when it merely happens to be compensated. Correctness that depends on nobody noticing the inconsistency is not correctness; it is luck with a long half-life.

G
Five ships of debt, paid

The script that was recommended five times

bin/verify-vault-inventory.sh was the standing recommendation at v250, v251, v252, v253 and v254. It was never written; bin/ did not exist. So this ship wrote it, ran it against the vault, found two bugs in its own first draft, fixed them, and ran it again.

This subject's contribution is the correction to clause 2. v254 specified it as “filename-label versus newest entry” — which, implemented literally, flags Griffiths' correct README as broken. So the clause does not ask does the label match the content. It asks is the lag declared.

== CLAUSE 1 — bidirectional chapter inventory == FAIL named in CLAUDE.md but ABSENT from _state/: (a rename never swept) FAIL present in _state/ but NEVER MENTIONED in CLAUDE.md: 5 files == CLAUSE 2 — label lag must be DECLARED, not merely compensated == PASS 03c: label v183 lags content v255 — lag is DECLARED (the v245 fix, machine-confirmed) FAIL 03c: THE DECLARATION IS ITSELF STALE — says 'through v250', file holds v254 == CLAUSE 5 — CLAUDE.md size budget == FAIL 200,352 bytes over budget; 30 accreted head blocks
Clause 2b, which I did not expect to need

The source-of-truth notice added at v245 to compensate for the wrong filename had itself gone stale by four ships — the third time (v247 → v250 → v254), and the first time a machine caught it. The v245 fix worked exactly as designed: the wrong label has been harmless for 71 ships because it was declared. Nothing was checking the declaration.

A declaration is a claim, and claims need checking too.

And the spec was already in the file

That same notice, written at v250, reads: “The fix for this file is not another prose note — it is bin/verify-vault-inventory.sh… a bidirectional check whose third clause compares each filename label against the newest entry it actually contains, and FAILS.” The vault wrote the specification inside the file the script is meant to check, and then did not write the script for five more ships.

Two bugs in my own first draft

The draft resolved the vault root with a relative path, landed in the wrong directory, and clause 1 reported PASS by comparing two empty sets — a green check that checked nothing, which is this page's own section E reproduced inside the tool built from it. Fixed by resolving the root by signature and adding a nonvacuous guard.

The second: a bare v[0-9]+ pattern matched v89 inside the GitHub username luongnv89, making an archived chapter appear to hold a v89 entry. Fixed by parsing heading lines only, with a word boundary — which is what the vault's own notice had specified all along.

H
The lesson

Displacement, not divergence

Every recent subject in this corpus failed in the same direction. v250 wrote six rules it called non-negotiable and gated one. v251 built a measurement instrument and pointed it only at the arm that could not fail. v252 ran one arm of a three-arm eval and published the comparison. v253 wrote a word budget into a commit message and watched it breach at twenty-one times the rate. v254 built a weekly CI job and aimed it at the single property of its file nobody doubted. In every case a check was missing, misaimed, or unenforced, and the artifact drifted away from its own claims.

This repository has no checks at all, and it did not drift. Not one byte has changed since 2017-05-23.

That is a different failure mode. The last five ships were about divergence: the artifact changed, or its claims did, and nothing was watching the gap. This one is about displacement: the artifact held still and the ground moved under it. JCenter was retired. Google relocated its Maven coordinates and declined to bring the old plugin along. Android made permissions run-time, then made notification channels mandatory, then set an install floor at targetSdk 24. Each was somebody else's decision, taken years after the last commit.

No CI job Griffiths could have written in 2017 would have failed in 2021 when JCenter closed, because the failure is not in the artifact. There is no predicate over these 578 files that is true in 2017 and false in 2026. The bytes are the same; only their meaning changed.

What can be done about displacement is much smaller and much duller: say when you were right. Not “this is deprecated” — the author could not have known — but “this is the first edition, it targets API 21, it was last verified in May 2017, and the current edition's code is over there.” Six lines. They would have cost nothing in 2017 and they would be worth a great deal now.

The consequence is measurable. Those figures make the obsolete first edition the most discoverable Head First Android repository on GitHub — 3.8× the stars and 4.0× the forks of the repo holding the Kotlin code for the book that is actually in print. A learner searching GitHub finds the 2015 Java code first, and nothing in it points onward.

Meanwhile Android itself, at every launch, displays the sentence the README declined to write.

You cannot document a failure mode that does not exist yet. You can only date your work.
