Tool-Surface Anchoring

xiaobright/dsh-anchored-standard · MIT · v0.1.0 · ~3,500★ (page-stated) · maintenance-only since 2026-08-17

A DeepSeek Harness preset built on one claim: the model reasons differently depending on how many tools you show it on the first request. The mechanism is real and carefully built. Whether it makes the model better is the part nobody could reproduce — and the author shut the project down because he could no longer afford to check.

The mechanism

Look like Minimal on request #1, become Standard from request #2

DeepSeek ships two presets for its harness. Minimal exposes two tools and scores well on their internal evaluation. Standard exposes twenty-five and scores worse. This preset tries to have both: it constrains the first model request to Minimal's real two-tool schema, blanks every automatic context injection on that request, and then promotes to a fuller catalogue the moment the session records a durable event.

It is not a plugin that adds a feature. It is a composition of the host's own configuration rows — an agent preset — which makes it the third structurally distinct kind of DeepSeek Harness extension the corpus has now documented, after the host itself and two kinds of plugin.

The three levers

What actually moves the model's first reasoning chain

LEVER 1

Tool schema

The decisive variable at the adapter's default output budget. The real Minimal pair anchored 5/5; every Standard-family schema fell back 11/11.

LEVER 2

Output budget

A 1024-token cap on the first request also anchored it — 26/32 — independently of the tool descriptions. Left unset by default; opt-in only.

LEVER 3

Injected reminders

With the skill catalogue present the effect vanished entirely: 0/9. Roughly 9 KB of auto-injected text was enough.

Lever 3 is the one that generalises, and it explains why replication kept failing on other people's machines: the harness injects the skill directory only when local skills exist, so the author's machine could reproduce the effect and everyone else's could not.

The load-bearing caveat

The two independent replications disagree with each other. One found the anchoring effect robust but its benefit statistically indistinguishable from zero. The other could not reproduce the effect at all on current model weights, and traced the score losses to a model-layer defect unrelated to the preset. Any use of this subject has to carry that.

To the author's credit, the README says a version of this itself — “treat the scores above as our original observations, not a settled effect size” — and documents the provenance correction that a third party forced on him. That is a stronger form of honesty than volunteering one's own gaps.

Why no new pattern

Anthropic already ships the mechanism

The tempting reading is that this is a new capability class: constrain the first request's tool surface to select the model's reasoning trajectory. It is genuinely unrepresented in the corpus, and the near neighbours all fail to cover it — graduated tool exposure for an MCP server is scoped to permissions and quota as a deployment-time flag; context compression is a token-economy interceptor; harness emulation swaps whole harness personalities; skill optimisation works on a document in text space.

But the mechanism is not new, and the closest prior art is a first-party Claude feature. Anthropic's Tool Search Tool with defer_loading: true strips deferred tools from the initial system prompt entirely and restores them on demand through a search tool — documented at 77K → 8.7K tokens on the first request. That is the same bootstrap → discovery → promote shape, shipped and supported. The academic literature is thick too: dynamic tool gating with lazy schema loading, work on how many tools an agent should see, and a body of results showing the first reasoning step disproportionately determines the outcome.

So what is distinctive here is not the mechanism but the rationale and the measurement. Every documented staged-tool system justifies itself with token economy or least privilege. This one justifies itself with reasoning-trajectory selection, then publishes the ablations and lets strangers fail to replicate them in public. That is a real contribution to understanding — and understanding is not a capability class.

How it ended

Killed by the cost of checking, not the cost of building

The farewell note is dated the day before this wiki was written. Development has stopped; the repository is maintenance-only.

API 涨价之后，一轮完整评测的成本已经超过了我的承受范围，而继续在没有验证能力的情况下堆功能，是对用户不负责任。

“After the API price increase, the cost of one complete evaluation round has exceeded what I can bear, and continuing to pile on features without verification capability is irresponsible to users.”

The handoff document prices it: an evaluation round went from roughly ¥2 to ¥12 — about $0.28 to $1.70. The absolute figure is trivial, which is exactly the point. The work needed many rounds, so a sixfold multiplier on a small number was enough. For inference-time research the binding constraint is the cost of evaluation, not the cost of development. Writing the plugin was free; knowing whether it worked was not.

The same note contains the sharpest statement of what the project actually was — sharper than the README's:

“Much of our recent work can be called ‘inference-time control’, or plainly: filling gaps for the official team — retrieving the good behavior the model was trained to show under evaluation conditions, back into the user's real-world environment.”

And it names its own obsolescence condition: that the vendor train across more diverse harness environments, citing Kimi K3's technical report as proof the path works, so that “our kind of patch engineering [becomes] unnecessary.”

Why this matters for your setup

Your tool catalogue may be a reasoning variable, not just a budget line

Your Claude Code session carries roughly a 54,000-token tool catalogue across connected MCP servers. The vault has treated that purely as a context-budget problem — and this session proved the point again when eighteen workflow subagents died at ~207K against a 200K ceiling.

This subject's evidence says the tool surface is plausibly also a reasoning variable. Issue #6 measured roughly 9 KB of auto-injected catalogue taking a reproducible behavioural effect from ~81% to zero. Your injection is about six times larger than the one that did that.

Be careful with the inference, though: what is established is a change in reasoning style. That it changes reasoning quality is precisely the claim two replications failed to confirm — and it was measured on DeepSeek V4 Pro, not on Claude. So this is a hypothesis worth testing on your own setup, not a finding to act on blindly.

The test is nearly free, because the lever already exists first-party. You do not need to install a dead preset for a rival harness to try the idea.

C11

Trial Anthropic's Tool Search Tool with defer_loading: true on your own Claude Code — and measure it.

Three real tasks, run with the full catalogue and again with most of it deferred; capture tokens through the ccusage/OTel layer and judge output quality yourself. Gives the cost-optimisation thread a second dimension it currently lacks.

Also worth taking

  • Fail-soft at runtime, fail-fast at config. A missing bootstrap tool degrades to the full catalogue with a one-time warning so composition drift cannot brick a session — while an invalid setting throws at mount.
  • Blank the family, don't enumerate the sources. The gate suppresses the whole runtime-context family rather than named sources, so an unknown third-party injection is caught by default.
  • The handoff document's evaluation discipline. Measure the artifact the downstream process consumes, not the pre-cleaned one. Label small-n results as exploratory and tag every run with its invariants. Design probes that isolate one variable at one request per trial. Watch for silent model-checkpoint drift.

Risk

Unusually clean supply chain, three real hazards

Zero npm dependencies, no lifecycle scripts, no network calls, no telemetry, CI with read-only permissions, atomic writes confined to the harness home directory, and an installing-agent contract bounded to one command. For what it is, that is exemplary.

Do not

Do not install the prefab modes. They replay 80 KB and 212 KB of another person's recorded model reasoning into your session as history, with stale tool results replayed verbatim — only skill-search results are re-rendered against your machine. That is a self-inflicted context-injection surface.

Do not cite “Project2 98/99.” The repository's own issue #60 retracted the attribution and nobody has reproduced the number.

Do not expect sandboxing from the bundled shell on Windows. Its own tool description says it runs without OS sandbox confinement and to treat output as untrusted.

Two documentation defects found by hand: the README links a HANDOFF.md that does not exist in the repository, and third-party plugin directories disagree with the repository about its licence and star count. The repository is authoritative — the same lesson the previous two ships in this dependency graph produced.
