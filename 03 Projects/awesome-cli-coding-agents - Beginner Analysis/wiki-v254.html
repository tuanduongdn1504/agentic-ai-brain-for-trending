One field of five

A weekly build server keeps 300 curated entries in perfect star order — and reads one field of the five that the very same API response hands it.

bradAGI/awesome-cli-coding-agents  ·  HEAD 6e307e73  ·  two clones, diff -rq clean both ways

the finding

What the machine asks for, and what it throws away

The list is one Markdown file — 300 entries, 688 lines — plus a banner, a 192-line Python script, and a GitHub Actions workflow that has fired every Monday for seventeen weeks without a gap. Each run re-fetches every entry's star count, re-sorts all six sections, stamps the date, and commits. It works. That is the unusual part.

The whole story is one line of that script:

return json.load(resp).get("stargazers_count")

The entire GET /repos/{owner}/{repo} response is parsed into a dictionary. One key is selected. The rest is discarded on the next line — and each of those keys is the answer to a defect the list actually has.

stargazers_count
Read. Zero descending-order violations across 300 entries in six sections, and the numbers are right — I checked three against rendered GitHub pages: openclaw 386,827 vs 387k, claude-code 142,065 vs 142k, hermes-agent 233,195 vs 232k after three days of growth. correct, and verifiably so

Discarded. letta-ai/lettabot (327★) sits in the active Open Source section. Its GitHub title reads “Archived — has been replaced by Letta Code channels/schedules!” The list's own third inclusion rule requires a “valid, active project (no dead repos).” a dead project in the active list

Discarded. ruvnet/claude-flow — 68,000★, the second-largest entry in its section — redirects to ruvnet/ruflo. So does paoloanzn/free-code → freecodexyz/free-code. two stale names, one at 68k stars
pushed_at
Discarded. There is no decay or dormancy policy of any kind — no dated section, no per-entry evidence, nothing that detects a project going quiet. no dormancy detection at all
license
Discarded. 134 of 300 entries name no licence, and ten of the twenty most-starred are silent. The machine could have filled every one. you cannot filter this list by licence
and the sixth thing, which needs no API at all

300 entries, 295 unique URLs. Five duplicate pairs — every one adjacent, every one byte-identical. The script builds repos, a dictionary keyed by (owner, repo), so building it is deduplication. Twelve lines later it prints len(repos) to stderr.

Every Monday for seventeen weeks that job has printed 295 while editing a file containing 300 entry lines. Nothing compares them. One if, on data already in hand, already being printed.

provenance

The duplicates came from transcription, not tooling

Traced through all 125 commits, the duplicate count is a clean step function: zero from the root commit through 2026-07-27 — 5.7 months and 242 entries — then five, in a single commit, and exactly five ever since.

The file has been completely machine-rewritten four times since they appeared. All four preserved them. And because the sort keys on stars, identical entries sort adjacent every run — the machine actively holds them side by side, in the one arrangement a human reader would most easily notice.

Nine commits are batches phrased “Add N entries from reviewed PRs.” The maintainer reads contributor pull requests and re-types their entries. He also has 33 real merge commits. Every duplicate came from a transcription batch; not one came from a merge. Git already knows what is in the file; reviewing a PR and hand-copying it is the one workflow that discards that knowledge.

the rule

A declaration is a form of aim

Three classes of fact in this repository had three different fates, and the pattern is not “machine good, human bad.”

  • What the machine was aimed at — stars, sort order, the “Last updated” stamp — is correct and verifiable. The stamp reads 2026-08-17 because a sed step writes it weekly.
  • What the human declared — the headline “110+ CLI coding agents” — is exactly right. Agents are 83 + 12 + 16 = 111; the harnesses are “plus.” 111 + 189 = 300. He bumped that number by hand in five separate commits.
  • What nobody declared and nothing was aimed at — uniqueness, liveness, rename-freshness — is broken.

A gate's aim, not its quality, decides what rots — and a declaration is a form of aim. Before adding a check, ask what you have never declared. That is where the rot is.

I assumed “110+” was stale against 300 entries. It is not, and three separate fleet agents made the same misreading. The sentence's grammar was precise all along.

replication

The length ladder, measured against verified stars

v253's maintainer diagnosed that entry length tracked how hard each submitter wanted to promote their own project. That was measured against hand-typed stars. Here the stars are machine-fetched weekly, so the same association can be measured properly. Mean description words, by star bucket:

The seven most-starred projects average 19.3 words and not one exceeds 28. The 104 least-starred average 31.2, and 21 of them exceed 40. openclaw at 387,000★ gets 19 words; Agent AFK at 51★ gets 71 — a 7,588× spread in adoption inverted into 3.7× in words.

And the structural consequence is specific to this list, because it sorts by stars: the file gets systematically wordier as you scroll, so promotional pressure and position are correlated by construction — concentrated exactly where a maintainer's attention runs out.

the honest read

A Spearman of −0.24 on n=287 is statistically significant but explains roughly 6% of the variance. The bucket means are a far clearer signal than the coefficient. And the causal story — that length tracks self-promotion — is v253's maintainer's diagnosis of his own list, stated in his own commit message. It is not established here, and a perfectly innocent alternative fits this data: niche low-adoption tools genuinely need more words to explain what they are.

The defensible claim is that the association replicates against verified stars. Not the motive.

One difference matters: v253 had a budget nobody enforced and landed at mean 18 words. v254 has no budget at all and sits at 27.6. That is the cost of not writing the number down.

The silent detector returns zero — and the null sharpens the rule

Second consecutive null, and I ran it rather than assuming it. v253's explanation was that a curated list has no runtime — it cannot fail confidently. But v254 has a runtime: 192 lines running unattended every Monday. It still returns zero. So the detector's domain is not artifacts that run — it is artifacts whose authors have debugged them.

And this runtime fails silently exactly where it matters. An HTTPError prints one WARN to stderr in an unattended weekly CI log, then the sort key falls back to re-parsing the badge already printed in the file — so a dead repo keeps its last-known star count forever, rendered as current fact. Worse: if every fetch failed, the script still rewrites the file, git diff --quiet finds no change, the step prints “No changes.” and exits 0. A total API outage produces a green, successful run indistinguishable from a quiet week.

A warning in an unattended job is a silent failure with extra steps.

Error ledger — 19 caught, 6 mine, and the fleet's worst was a fabricated verdict

Mine: the median was 26 and should be 25.5 (I took the upper-middle rather than averaging the two middles) · I assumed “110+” was stale, and it is exact · a loose URL regex produced non-comparable unique counts · my corpus matcher had two false-negative classes, and closing them took the ship count from 13 to 16 · my self-submission matcher cannot see company accounts or non-GitHub URLs at all · I nearly compared 45.5% to v253's 18.3% across different denominators.

The fleet's worst: the critic declared the root commit date and commit count “CRITICAL fabrications,” escalated to “the entire edifice is compromised… no claim built from it can be trusted” — and was itself wrong on both. The root is 0b3d5227, 2026-02-06; the count is 125; each confirmed three ways. A fabricated verdict was used to destroy correct work — a worse failure mode than the previous ship's, where fabrication merely added a false finding.

The mechanism is a portable rule. The verifier used git log --reverse --oneline | head -1 as a proxy for “the root commit,” and got a real commit that is not a root. To establish a structural git fact, use the command whose semantics are the definition — rev-list --max-parents=0 for roots, rev-list --count for counts. Never log | head or log | wc.

Also: a description-length figure of “median 23.5” came from sed 's/.*— //', which is greedy and truncates at the last em-dash. Fifteen of 300 entries contain more than one. Re-running with the greedy method reproduces 23.5 exactly, which proves the method was the cause.

Point an adversary at the critic. The final synthesis is the only stage with no adversary, and the only one whose output reads as authority.

Rung 1, two hours, zero installs. Finally write bin/verify-vault-inventory.sh, recommended for four consecutive ships and still unwritten. Seven clauses now, from five ships — and clause 7 is new here:

clause 7 — and note its exact form

The subject's script already computes the deduplicated set and already prints its size. It simply never compares that number to the other number sitting right next to it. So the clause is not “add a dedupe check.” It is: wherever the script already knows a count, assert it against the count it is supposed to equal, and fail if they differ.

Then clause 8, a rename clause — the list carries claude-flow when the repo is ruflo, and my own overlap check missed two vault ships for exactly that reason.

And give the stale pattern rows a Resting section by hand. That pass has been deferred for roughly 66 ships because deletion demands certainty while moving a row is reversible. This ship is the argument for not waiting on automation: v253's hand-maintained decay section correctly caught an archived project that v254's weekly CI job missed.

pins

What not to trust, and the one thing you now can

  • Verify every licence yourself. 55.3% is 25× better than v253, but ten of the top twenty are silent.
  • Presence is not a safety or quality endorsement.
  • Never point an agent at this file and say “install the best one” — 300 untrusted descriptions become 300 attempts to steer that choice.
  • An active entry is not necessarily alive; a listed name is not necessarily current.
  • Do not repeat “fastest repo in GitHub history to 100K stars” or the “March 2026 source leak” as fact.
  • Do not repeat the fleet's numbers: not 50 commits, not a 2026-04-06 root, not median 23.5, not worktree at 3%.
the one pin that reverses

You may cite v254's star figures as CI-fetched and spot-verified, within a one-week refresh window. v253's standing pin was never cite its star figures as verified. This is the one thing the machinery unambiguously bought — and it bought it well.
