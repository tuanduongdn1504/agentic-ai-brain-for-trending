What it is

§1The compute substrate, finally read as a subject

OpenSandbox is a self-hostable control plane that provisions, runs, inspects, snapshots and destroys isolated sandboxes for AI agents. A FastAPI lifecycle server, two runtime backends (Docker and a full Go Kubernetes operator), SDKs in six languages, an osb CLI, a first-party MCP server, six installable agent skills, and 26 runnable examples — nine of which target a different coding agent.

For 243 wikis this corpus read things that stand on sandboxes — a live preview here, a Kali container there, worktrees, a plugin seam — without once reading a sandbox. E2B appears fourteen and ten times across the vault’s state files, and every single occurrence is a dependency inside another subject. This is the first subject that is the floor.

The document that decides who owns the project does not name Alibaba, and the CI job that must pass on every pull request will not let any file omit it.

Nothing here is dishonest — every fact is in the tree. withdrawn I opened this analysis thinking the affiliation was concealed, and that framing is withdrawn: it is disclosed in 1,674 copyright headers and every package-manager coordinate the README tells you to install. The only place it is missing is the org page. That correction exonerates the project, and it leaves something more precise in its place: documents are cheap to neutralise; build gates, module paths, package coordinates and copyright headers are not — because those are the ones with downstream consumers.

Both bridges are drift-proof — the stub carries no content to go stale. But they are not equivalent: the symlink delivers the content, while the stub costs the agent a second read and a hop it may not take. The symlink sits in a subdirectory. The root — the file Claude Code opens first — got the weaker one.

v243 made the mirror-image error: it symlinked so two files could not diverge, then hand-copied one warning paragraph into three skill files where it came out different three times. Two unrelated companies, opposite mistakes, one cause: whatever a machine does not generate, humans will let diverge.

Which lands at home. This vault’s _state/03c-projects-v61-v183.md has held entries through v244 for sixty-one versions. Four consecutive ships have diagnosed exactly that defect. None of us has run ln -s.

Security

§5The first right answer to a failure mode this corpus keeps finding

verified framing withdrawn A consent gate that fails closed

The server binds 0.0.0.0 by default, api_key defaults to None, and middleware/auth.py:85 reads “if no API keys configured … skip auth.” I first wrote that as auth fails open. That was wrong. startup_guard.py refuses to start the server without explicit acknowledgment:

  • OPENSANDBOX_INSECURE_SERVER=YES — the non-interactive path, logged as a warning
  • otherwise, on a TTY: an ANSI-red prompt demanding the exact string YES, with a 30-second timeout that aborts and a link to tracking issue #750
  • otherwise: a hard RuntimeError — “Startup blocked…”

Documented in four places and four example configs, two of them in Chinese. The vault recorded a broken-authentication triad at v231 and v232 — both pilot-AVOID, both shipping this exact convenience default with nothing in front of it. This is the first time the corpus has seen the right answer, and it is about sixty lines of it.

unverified — flagged, not concluded The finding that survives

middleware/auth.py:82-83, evaluated before the key check, skips authentication for /v1/sandboxes/{id}/proxy/{port}/… in single-tenant mode — even when an API key is configured. OSEP-0011 and the [ingress.secure_access] signed-token machinery exist to protect those endpoints, so the intent is plainly that the proxy layer carries its own scheme. I did not verify end-to-end whether a token is required when secure_access is unconfigured, and that is the question that decides whether this is a design boundary or a hole.

The shape holds regardless: the consent gate protects the operator who configured nothing, and a separate code path un-protects the one who configured something.

verified “Strong Isolation” is a passthrough — and the honest part is the part the README hides

gVisor, Kata and Firecracker appear only in the README, in config validation, and in tests. There is no integration code — just a runtimeClassName passed to Kubernetes. You install the runtime. But the validators encode something genuinely useful that the marketing bullet obscures: test_rejects_gvisor_with_network_policy versus test_allows_kata_with_network_policy. Choosing their strongest isolation turns off their egress control.

Method

§7Three new rules, one of them earned by refuting my own fleet

refuted D29 — mtime is not drift; test the claims, not the date

A completeness critic reported cli/AGENTS.md as “67 days stale.” I tested every path it names — eleven of them — and all eleven exist. The file had not changed in 67 days because it was still correct. Staleness is content disagreeing with reality, not a timestamp — and this is the rule that decides whether the vault’s planned verify-vault-docs is a linter or merely a recency alarm.

D28 An absent config file is not an absent check

All 24 workflows grep zero for CodeQL, trivy, gosec, bandit, semgrep, scorecard or snyk, and there is no dependabot.yml. Concluding “no security scanning” would be wrong: 18 Copilot Autofix commits and 5 dependabot/ branches prove both run through GitHub’s settings, which leave no file in the tree. A tree-only audit systematically under-reports security posture — and the detector is the bot’s commit trailers, not the workflow directory.

The ruling

§8Mint at N=1 — and the argument against it

“Self-Hostable Sandbox / Code-Execution Runtime for AI Agents” — corpus-first for the surface, explicitly not world-first. It is the last missing member of a family this corpus mints repeatedly: browser (v41), iOS simulator (v183), web reach (v174), Office documents (v206), stealth browser (v179), database (v212), file search (v194), video (v198). All answer what can the agent reach? — and the one an agent needs most, somewhere safe to run code, was absent.

reviewable The case against is genuinely strong, and it is recorded, not buried: kubernetes-sigs/agent-sandbox standardised this shape at KubeCon in November 2025 — three months before OpenSandbox’s public launch — and OpenSandbox supports that standard rather than setting it. When a Kubernetes SIG owns the category, it is an established industry class. Add that OpenSandbox delegates isolation rather than implementing it, that E2B and Daytona precede it as products, and that fame is not a mint. This is the closest mint call since v233.

One fact reframes its position without earning it anything: Daytona went closed-source in June 2026. The leading open-source self-hostable rival left the category two months before this analysis — not because OpenSandbox won, but because the incumbent walked away.

Recorded, not executed — flagged to the audit

The committed cross-harness agent-context bridge now stands at N=3 — v213 Intel geti, v243 ToolJet, v244 OpenSandbox: three independent, cross-author, cross-domain, non-port instances. That crosses the corpus’s eligible-at-N=3 threshold, so a promotion is live on the table. I am not taking it: a promotion is an audit act. But the audit should note that the three are not the same mechanism, and that both multi-instance cases are partial — ToolJet at 3 of 13 directories, OpenSandbox at 2 of 6 with two incompatible mechanisms inside one repository. The pattern’s real-world form is incomplete adoption, and the row should say so.
