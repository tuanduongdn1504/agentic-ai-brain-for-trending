## Core claims / thesis (extracted, main-loop reading)

1. **System thinking (tư duy hệ thống) is the one coding skill that gains value under AI**, not loses it —
   previously accreted accidentally over years of on-the-job pain; now the core competency for every SWE.
2. **Programming = theory building (Naur).** Code is the shadow; the real program (how components connect,
   why they work, what breaks if you pull a link) lives in the developer's head. Vibe-prompting tempts us to
   *stop building the theory*.
3. **A system is not a pile of parts** thrown together — it's a model where components affect each other over
   time; change one, another reacts; drop a link, the whole model can stop working. **Code is the instrument;
   the system is the music; the developer is the conductor.** AI can play any instrument, never the conductor.
4. **Prompting is the easy, ever-cheapening layer.** The durable skill is system/architecture/design thinking.
5. **Compiler vs LLM:** a compiler is *deterministic* (same input → same output; trust without understanding).
   An **LLM is a probabilistic translator** — "a collaborator you can only trust when you understand what it
   just did." Even if AI writes the whole project, you must verify.
6. **"Cheap" vs "easy":** AI makes coding *easy*, not *cheap* — the price is deferred as **technical debt**
   (wrong structure, hard-coding, dirty data, no rate-limiting, 1000-line God components). Apps run fine at
   10-20 users then die at scale ("running only because it hasn't hit the point of collapse yet").
7. **Jagged technological frontier (Harvard):** AI is astonishingly sharp in some spots, absurdly dumb in
   others — within one session/model. The operator must know where the "silent failure" zone is.
8. **The junior crisis:** seniors have system thinking because they earned it through breaking systems and
   getting yelled at. AI severs that "struggle school". Harvard/62M-records: GenAI (since 2023) cut junior/
   entry hiring. But 2026 shows reversal (IBM ~3× entry-level) because firms can't refill the senior pipeline;
   in-house-grown talent (knows the business + the existing system) beats externally-hired generalists.
9. **Fast-food analogy:** AI coding = fast food — useful only once you know what a 5-star meal tastes like.
   New grads whose "first meals" are all AI never learn the standard, so they break in production.
10. **Deliberate practice (athlete analogy):** average engineers get weaker; deliberately-trained ones get
    much stronger — the gap (and the money) widens. The 20-30% who cross the valley become more valuable than
    any prior generation.
11. **Role-specific strategy:** Junior/Fresher → use AI as an infinitely-patient *teacher* (ask why/trade-offs,
    not "write my code"); weekend hand-coding to keep the muscle. Senior/Middle → stop hand-coding for pride;
    use scars for architecture, review, sharp judgment on top of AI. Founder/PM → vibe-code is valuable, but
    you MUST have system thinking + know when to hire a real engineer + own your VPS.
12. **AI replaces typing, not thinking.** System thinking amplifies you if you have it; it exposes you if you
    only copy-paste/generate. Learn to slow down deliberately even though AI lets you go fast.

## 3 GOLDEN QUESTIONS (answer BEFORE running code) — [11:16]

1. **State / data flow — where is state stored, who is the single true owner?** If two components each think
   they own the data, you've armed a time-bomb. (Prioritize data/DB architecture over UI.)
2. **Feedback — where do signals come back from? What tells you the system is healthy or erroring; where is
   error logic collected?** Without this the system only *pretends* to run before total collapse.
   (Do you need self-destruct/chaos tests before launch?)
3. **Blast radius — what breaks if I delete this part?** Can you trace a component's zone of impact / the data
   flow / the user flow *in your head*? If not, that's a cognitive hole — you don't understand your own system.

## 4 PRACTICE STEPS (deliberate training of the "brain muscle") — [33:44]

1. **Design before you prompt.** Pen + paper / iPad. Draw boxes = components, arrows = data flow; mark where
   state lives, where errors can happen, where you can decouple. "If you can't draw it, you don't understand
   it — and AI will invent the parts you didn't draw." For backend: draw/understand the ERD before coding;
   ERD → API → spec, else it's guesswork that eventually collapses.
2. **Use spec as scaffolding (specification-driven).** Write WHAT and WHY before HOW. A short spec defines the
   problem, constraints, trade-offs, definition of success, and the error scenarios you must test. The safest
   skeleton for working with coding agents (so it dodges the traps).
3. **"Case-study when something breaks" thinking (chaos-delete drill).** Pick any file/function, (mentally)
   delete it: how badly does the system break, what breaks? You'll learn each part's role. "I don't know" =
   a cognitive hole. Cao Cao: "use but don't fully trust" — use AI, but stay in control; always test.
4. **Reverse code review — argue with the AI.** On important PRs don't merge fast; make the AI explain each
   step ("why did you write it this way, did you weigh the risk, is it extensible, what's the trade-off?").
   Best form: **make the AI write the docs/tests for the whole project**, then you review/edit/validate the
   docs and ask back. Treat the LLM as an infinitely-patient teacher you must continuously verify (10 asks of
   the same question → 10 different answers; it is NOT a compiler).
