What it is

The vault’s own architecture, built by someone else for client work

An agent-skill collection plus templates that scaffolds a knowledge graph the AI reads and writes over time: atomic concept notes, [[wiki-links]], a lifecycle of emergent → validated → canonical, and a SENSE → ORIENT → ACT → DEPOSIT loop. Thirteen skills, 8,243 lines of markdown, one author, MIT.

Its stated principle is stigmergy — and it is the most interesting sentence in the README:

Desire paths are stigmergy. Agents coordinate by reading and modifying the shared environment — not by following procedures. If a file has zero heat, it’s the concrete path nobody walks. Pave the desire paths.README.md

This is Karpathy’s LLM-wiki pattern — the same pattern this vault runs by hand — productised as a Claude Code plugin. That makes it unusually on-goal, and a fair mirror.

The headline

The repository ships the exact document that forbids its own README’s claim

The refactor is real and brave. git diff v1.0-ceremony..v2.0-stigmergic is 8 files, 158 insertions, 448 deletions — a net −290-line deletion, with both sides tagged so it is diffable. They deleted the taxonomy and ontology templates, a /graph-health command, and an entire ingestion subagent.

The justification is a measurement: “We measured it — taxonomy.yaml had 2 accesses in 90 days, ontology.yaml had 1, and the node lifecycle doc had zero.” That measurement is nowhere in the repository. No log, no artifact, no data — it describes client deployments and is unfalsifiable from the artifact.

But an instrument was here. eval_quickstart.py is a real Claude-Agent-SDK harness with a three-arm design (--version old | new | both). Its results file was committed, then deleted by f7619ba — “docs: rewrite README with v1→v2 narrative, drop eval results.” I recovered it.

Three things follow, each settled by command:

  • The baseline arm was never run. --version old needs eval_old_claude.md; that file was never committed — 0 of the 57 paths that have ever existed in this repository.
  • Seven of eight runs used zero tools. In a system whose thesis is that agents coordinate by reading and modifying the environment, its own recorded runs mostly recited the CLAUDE.md instead of touching the graph.
  • Nothing is graded. pass_criteria, fail_criteria and critical_fail appear only in their definitions and in a print() for a human to eyeball. Zero hits for score, judge, verdict, assert. The recorded fields are duration, tool count and response length — mechanics, never correctness.
And then the self-refutation

The repository ships statistical-validity-checks.md, 256 lines against “the backwards-reasoning failure mode.” Its own checklist: “‘N=8 is enough to see the pattern’ — no, N=8 fits ANY pattern perfectly by accident” and “same test set you iterated on?” Its §5: “Labeled N < 30 → do NOT iterate. Produce a ‘hypothesis-generating’ output labeled as directional.”

Their evidence base was N=8, single-arm, ungraded — and the README states the comparison as settled fact in a six-row table. The best document in the repository forbids the inference the README makes.

The borrowable rule: an instrument you only point at the arm that cannot fail is not a measurement. The harness was kept and the reading was dropped — the exact inverse of v251, where the instrument shipped and no reading did.

A functional defect

A hard STOP that routes nowhere

eval-loop/SKILL.md references a sibling skill ten times, in the strongest language in the repository:

STOP. Route to /eval-driven-scoring and read references/statistical-validity-checks.md. Do not proceed with this skill.eval-loop/SKILL.md:43

eval-driven-scoring does not exist in this repository. Existence-testing every path that file cites: two resolve, three dangle — including the statistical document itself, which is present but at eval/, not the references/ its own skill points at. One cited rubric was never tracked at all.

Why this matters more than doc rot

A predictive-scoring problem — lead scoring, candidate matching — hits a hard stop, is routed to a skill that isn’t installed, and told to open a file at a path that doesn’t resolve. The reference paths still point at the private parent skill this was carved out of: the gate shipped, the gatekeeper didn’t.

The fleet’s critic called this route “a REAL hard stop… genuinely fail-closed.” It is wrong on both halves: it is a markdown table cell, and its destination is missing. A stop instruction with no destination is a dead end, not a gate.

What is genuinely good

Two documents better than most published work on their subjects

statistical-validity-checks.md — 256 lines

An operational runbook on ground-truth contamination in LLM scorers. Its first gate is a contaminated/clean source table: “Contacts associated with closed/won deals” → “Pre-filtered on the outcome you’re predicting. Using outcomes as predictors = tautology.” Then a selection-bias template, a base-rate requirement, a discriminative-ratio band, a holdout procedure with a gap-interpretation table, and a backwards-reasoning detector that ends: “If you cannot describe falsification → the hypothesis is unfalsifiable. Do not use.”

All four of its worked ratio examples check out arithmetically. And it disclaims its own novelty: “not novel; they are table stakes… This document codifies them at the skill level so they become unavoidable.”

landmine-patterns.md

Pattern 1: two directories declaring the same deploy-target name with identical bindings — “A deploy from either location overwrites the other’s code with zero warning.” Translated across Cloudflare, Railway, Vercel, Fly and Compose, with a real detection method and a conditional severity taxonomy (Drift → Landmine on schema change).

The best line in the repository — and it diagnoses this vault

“Code drift fails loud (eventually — when a deploy detonates). Context drift fails silent — an agent reads the wrong context and nothing announces it.”

That is the -v183 filename and the C22–C27 stale-claim backlog, named exactly. A wrong deploy detonates; a wrong context just quietly produces worse work forever.

The installer — fetched and read, not executed

Why the answer is read-and-borrow

The critic claimed the CLI doesn’t exist and the install URL 404s. Refuted by direct fetch — it returns a valid 5.4 KB installer, and the binary ships. Reading it gives a far better-grounded picture than the repo alone:

  • The only integrity check is a size floor. MIN_SIZE=$((10 * 1048576)) — “should be at least 10 MB.” No checksum, no signature, no GPG, no cosign. Any ≥10 MB blob from that host installs and executes.
  • The version resolves at install time from curl -fsSL "$BASE_URL/latest.txt" — piping to bash installs whatever that mutable file points at, that second.
  • It auto-registers a login-persistent daemon at a 30-second interval. The README presents this as a step you run later. It is not.
  • A staging channel is one env var away. The binary is closed-source. There is no privacy or telemetry statement anywhere in the repository.

I did not establish that anything leaves the machine. But a closed binary polling your file access every 30 seconds from login, delivered by an unpinned pipe-to-shell whose sole integrity check is “is it at least ten megabytes,” is not a footprint to accept on a machine holding client or candidate data. In fairness, the script is competently written — the objection is the trust model, not the craft.
