The engineering worth the ship

A three-way decision on "the agent wants to stop"

internal/host/reminder/stop_guard.go:26-62
func NewStopGuard(...) agentcore.StopGuard {
  return func(_ context.Context, info agentcore.StopInfo) agentcore.StopDecision {
    ... return agentcore.StopDecision{Allow: true}
    ... return agentcore.StopDecision{Allow: false, Escalate: true}
    ... return agentcore.StopDecision{Allow: false, InjectMessage: inject}

Allow the stop, refuse and escalate, or refuse and inject a message telling the model what to do instead. Premature termination is the characteristic failure of a long-running agent, and this is the cleanest treatment of it in this corpus.

A budget kill-switch that waits for a safe boundary

internal/host/budget.go:17-18
budgetStopPending  // 已越线，等子代理边界停机
                   //   crossed the line; wait for a sub-agent boundary to stop
budgetStopped      // 已执行停机  — stop executed

and the test names are the specification:
TestBudgetSentinelWarnOnceThenBoundaryStop
TestBudgetSentinelJumpStraightPastLimit
TestBudgetSentinelHardStop  // BookUSD: 10, WarnRatio: 0.8, HardStop: true

Warn once at 80%, hard-stop at 100% — but do not kill mid-operation. Killing an agent mid-write corrupts the state you would resume from; entering a pending state and stopping at a sub-agent boundary keeps the checkpoint clean. And the nastiest case — cost leaping past the warn threshold in a single call — has its own test, which is why the warn and the stop must be independent checks rather than an if/else.

Loop detection for free, out of the state you already keep

internal/diag/runtime.go:37-38, 83
StuckStep  string  // 尾部连续同 step；"" = 不卡
                   //   trailing consecutive identical step; "" = not stuck
StuckCount int     // 连续次数 — consecutive count

rc.CurrentStep, rc.StuckStep, rc.StuckCount = analyzeCheckpoints(s.Checkpoints.All())

Read the tail of the checkpoint log, count consecutive identical steps, raise a severity — "StuckStep": SevCritical in the rule tests. It costs nothing extra, because the checkpoints already exist for resume. The general form is the transferable one: if you persist progress for resumability, you have already persisted a stuck-detector.

The centrepiece: routing is code, deciding is the model

My own read found the guards. It missed the architecture they hang off — which is the most valuable thing here. A fleet agent found it; its adversarial reviewer then caught three fabricated numbers in the same report. I verified both halves.

Scheduling lives instead in internal/host/flow/router.go — 160 lines ending in func Route(s State) *Instruction, a numbered decision table running cases 1 through 12 over persisted state. The Coordinator itself is an agent configured with agentcore.WithMaxTurns(100_000) at agents/build.go:314.

The pattern

The agent does not choose what to do next. Code chooses, from state already persisted for resumability, and the agent executes. Semantic work — planning, adjudication, writing — stays with the model; sequencing does not.

And cases 2, 4 and 5 are the discipline that makes it honest: the router explicitly declines to route when the decision genuinely belongs to the model, rather than pretending everything is mechanical.

The stall detector — the best twenty lines in the repository

internal/host/flow/dispatcher.go:112-140
// trackRepeat 记录连续相同指令的下达次数…
// 用 Agent+Task 相等性（不比 Reason，因为 Reason 是给人看的辅助文本）
// 次数恰好到 repeatNotifyAt 时在锁外触发一次 onRepeat

Four separate pieces of care in one small function:

  • Equality on Agent+Task only, deliberately excluding Reason — because Reason is human-facing prose that can vary while the instruction does not. A detector comparing the whole instruction would be silently defeated. He found that failure mode and wrote down why he excluded the field.
  • Fires once, exactly at the threshold — one alert, not a storm; router_test.go:289 asserts precisely that.
  • Fires outside the lock — a slow notification handler cannot block the dispatcher.
  • ResetRepeat() on resume, so recovery does not inherit a stale count.
The chain is complete

Router detects a stall from persisted state → dispatcher counts it on the semantic key → fires exactly once, outside the lock → notify runs a user command → killed on timeout if it hangs. The most complete unattended-safety path in this corpus.

And the philosophy is the transferable half: it does not hard-fail on a repeat. It injects the evidence and lets the model reason about the stall — the same move as StopGuard's InjectMessage. Instead of a retry limit: block the attempt, hand over the evidence, let the agent decide.

And twice, he tested the case where his own safety net would betray him

Checkpoints are idempotent by digest — "if the same Scope + Step + Digest already exists, skip the write and return the existing record" — so a retried tool call finds its own prior result. And checkpoints_test.go:71 is TestCheckpointStore_EmptyDigestNotIdempotent: two artifacts with no digest must not be treated as the same artifact.

That is the same instinct as TestBudgetSentinelJumpStraightPastLimit. In both places where his mechanism could produce a false negative, he wrote the test for it — which makes the absence of anything to run those tests the sharpest fact in the ship.

The rule, final form

Tests don't make you honest. They make you honest about the things they test — and only if something runs them. A test that nothing invokes is documentation.

And v263 is the most poignant of the three, because the tests are good: 916 lines for the context builder, 579 for chapter commit, 496 for foundation saving. The only thing that has ever run them is a person who remembered to type go test ./....
