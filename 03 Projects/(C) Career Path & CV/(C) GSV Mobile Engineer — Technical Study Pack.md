# NestJS & Backend Contributions for Mobile Engineers

### What NestJS Is

**NestJS is an opinionated, TypeScript-first Node.js framework for building scalable server-side applications.** It sits between Express (minimal, unopinionated) and a full framework like Django/Rails (highly opinionated). 

- **Core philosophy:** structured layers (controllers → services → repositories), dependency injection, decorators, and a clear module system
- **Inspired by:** Angular's architecture and TypeScript decorators
- **Current stable:** v10.x (2024+) with v11 in RC; you'll see v9.x in older projects
- **Language:** TypeScript by default (not JavaScript); works with Babel for compatibility
- **Router:** Express under the hood (NestJS wraps Express for HTTP handling); can swap for Fastify
- **ORM integration:** TypeORM and Prisma are the standard choices for PostgreSQL

**Why it matters to you:** A mobile engineer contributing to the backend will be adding endpoints, DTOs, guards, and queries inside an NestJS service layer. You don't need to architect the system, but you need to **read and extend** existing modules following their patterns.

---

### Architecture: Modules, Controllers, Services, Providers

NestJS organizes code into **modules**, each containing controllers, services, and other providers.

#### Module (the container)
A module groups related functionality. Typically: one domain = one module.

```typescript
// users.module.ts (NestJS pattern)
import { Module } from '@nestjs/common';
import { TypeOrmModule } from '@nestjs/typeorm';
import { UsersController } from './users.controller';
import { UsersService } from './users.service';
import { User } from './entities/user.entity';

@Module({
  imports: [TypeOrmModule.forFeature([User])],  // Load the User entity
  controllers: [UsersController],                 // Route handlers
  providers: [UsersService],                      // Business logic
  exports: [UsersService],                        // Share service to other modules
})
export class UsersModule {}
```

**In Express, you'd scatter routes across one file or multiple router files.** NestJS makes this explicit per module.

#### Controller (routes and HTTP concerns)
Handles HTTP requests, calls services, returns responses. Decorators define routes.

```typescript
// users.controller.ts
import { Controller, Get, Post, Param, Body, Query } from '@nestjs/common';
import { CreateUserDto } from './dto/create-user.dto';
import { UsersService } from './users.service';

@Controller('users')  // Base path: /users
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Get()  // GET /users
  findAll(@Query('role') role?: string) {
    return this.usersService.findAll(role);
  }

  @Get(':id')  // GET /users/123
  findOne(@Param('id') id: string) {
    return this.usersService.findOne(+id);
  }

  @Post()  // POST /users
  create(@Body() createUserDto: CreateUserDto) {
    return this.usersService.create(createUserDto);
  }
}
```

**Express equivalent:**
```typescript
// Express pattern
router.get('/users', (req, res) => {
  const role = req.query.role;
  const data = usersService.findAll(role);
  res.json(data);
});

router.post('/users', (req, res) => {
  const data = usersService.create(req.body);
  res.json(data);
});
```

**Key difference:** NestJS uses decorators and **dependency injection** (see below); Express uses explicit middleware and request/response objects.

#### Service (business logic)
Pure business logic and data access. Services are **providers**.

```typescript
// users.service.ts
import { Injectable } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { User } from './entities/user.entity';
import { CreateUserDto } from './dto/create-user.dto';

@Injectable()  // Marks this as an injectable provider
export class UsersService {
  constructor(
    @InjectRepository(User)
    private readonly usersRepository: Repository<User>,
  ) {}

  async findAll(role?: string) {
    if (role) return this.usersRepository.find({ where: { role } });
    return this.usersRepository.find();
  }

  async findOne(id: number) {
    return this.usersRepository.findOneBy({ id });
  }

  async create(createUserDto: CreateUserDto) {
    const user = this.usersRepository.create(createUserDto);
    return this.usersRepository.save(user);
  }
}
```

**Why a service:** separated from HTTP concerns; testable in isolation; reusable (can be called by other controllers, GraphQL resolvers, or scheduled jobs).

### Dependency Injection & the IoC Container (The Big Mental Shift)

This is the **single biggest difference** between NestJS and Express.

#### What it is
**Dependency injection (DI)** means: the framework creates instances of classes and **injects** them where needed, instead of you manually instantiating them.

```typescript
// NestJS: You declare the dependency, NestJS provides it
constructor(private readonly usersService: UsersService) {}

// Express: You manually create/require the service
const usersService = new UsersService(db);
app.get('/users', (req, res) => {
  const data = usersService.findAll();
  res.json(data);
});
```

#### Why it matters
- **Single instance:** NestJS creates one instance of `UsersService` (singleton), reuses it everywhere
- **Testable:** In tests, you swap the real service for a mock without changing the controller
- **Decoupled:** Controller doesn't need to know *how* to create a service; the framework handles it
- **Lifecycle:** NestJS manages creation, initialization, and cleanup

#### The IoC Container
NestJS has an **Inversion of Control** container that:
1. Reads your `@Module()` declarations
2. Builds a dependency graph
3. Instantiates providers in order
4. Injects them into constructors
5. Boots the app

```typescript
// App bootstrap
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);  // IoC container starts here
  await app.listen(3000);
}
bootstrap();
```

**This is automatic.** You don't call `new` in your code; you declare dependencies and the container wires them.

### Decorators: @Module, @Controller, @Injectable, @Get, etc.

Decorators are **metadata** that tell NestJS how to handle a class or method.

```typescript
@Module({ ... })              // This is a module
class MyModule {}

@Controller('route')           // This is a route handler
class MyController {}

@Injectable()                  // This is an injectable provider (service, guard, etc.)
class MyService {}

@Get('/path')                  // Handle GET requests to /path
getMethod() {}

@Post()                        // Handle POST requests
@Put(':id')                    // Handle PUT /route/:id
@Delete(':id')                 // Handle DELETE /route/:id
@Patch(':id')                  // Handle PATCH /route/:id

@Param('id')                   // Extract route param
@Query('limit')                // Extract query param
@Body()                        // Extract request body
@Headers('authorization')      // Extract header

@UseGuards(AuthGuard)          // Apply a guard (see below)
@UseInterceptors(LoggingInterceptor)  // Apply an interceptor

@UseFilters(HttpExceptionFilter)  // Apply an exception filter
```

**Decorators are syntactic sugar.** Under the hood, they attach metadata to class prototypes. In Express, you'd define this in route handlers directly.

### DTOs (Data Transfer Objects) & Validation

A **DTO** defines the shape of data coming in or going out. NestJS uses **class-validator** to automatically validate request bodies.

```typescript
// create-user.dto.ts
import { IsEmail, IsString, MinLength, IsEnum } from 'class-validator';

export enum UserRole {
  Admin = 'admin',
  User = 'user',
}

export class CreateUserDto {
  @IsString()
  @MinLength(3)
  name: string;

  @IsEmail()
  email: string;

  @IsEnum(UserRole)
  role: UserRole;
}
```

#### ValidationPipe (automatic validation)
Apply the `ValidationPipe` globally or per-route to auto-validate and transform incoming data.

```typescript
// main.ts (global)
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,          // Strip unknown properties
    forbidNonWhitelisted: true, // Reject unknown properties
    transform: true,          // Transform strings to correct types (e.g., '123' → 123)
  }),
);

// Or per-route
@Post()
create(@Body(ValidationPipe) createUserDto: CreateUserDto) {
  return this.usersService.create(createUserDto);
}
```

**If validation fails, NestJS returns a 400 with validation errors.** You don't need to manually check types or patterns.

### Request Lifecycle: Middleware → Guards → Interceptors (Pre) → Pipes → Controllers → Services → Interceptors (Post) → Filters

**Order matters.** Understanding this is critical for interviews.

```
Request
  ↓
Middleware (global or bound)
  ↓
Guards (@UseGuards) — Is the user allowed? (auth check)
  ↓
Interceptors (pre-request) — Before controller (logging, timing)
  ↓
Pipes (parameter/body transformation & validation)
  ↓
Controllers → Services
  ↓
Interceptors (post-request) — After service (response transformation)
  ↓
Filters (exception handling) — If anything threw
  ↓
Response
```

#### Middleware vs Guard vs Interceptor

| Layer | Purpose | Example | Decision Point |
|-------|---------|---------|---|
| **Middleware** | Global or route-level request preprocessing | CORS headers, body parsing, logging | Runs first; cannot access route context |
| **Guard** | Authorization & authentication | Check JWT, check role/permission | Called before controller; can throw 403 Forbidden |
| **Interceptor** | Cross-cutting concerns (logging, timing, response transformation) | Log request/response, wrap response, cache | Has access to controller context; can modify request & response |

**Example: all three**
```typescript
// users.controller.ts
@Controller('users')
@UseGuards(AuthGuard)                    // Check if user is logged in
@UseInterceptors(LoggingInterceptor)     // Log this entire route
export class UsersController {
  @Get(':id')
  @UseGuards(RoleGuard)  // Check if user is admin
  getAdmin(@Param('id') id: string) {
    return this.usersService.findOne(+id);
  }
}
```

**Middleware example (Express-like):**
```typescript
// logging.middleware.ts
import { Injectable, NestMiddleware } from '@nestjs/common';
import { Request, Response, NextFunction } from 'express';

@Injectable()
export class LoggingMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    console.log(`[${new Date().toISOString()}] ${req.method} ${req.url}`);
    next();
  }
}

// users.module.ts
@Module({...})
export class UsersModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(LoggingMiddleware)
      .forRoutes(UsersController);  // Apply only to this controller
  }
}
```

**Guard example (NestJS-specific):**
```typescript
// auth.guard.ts
import { Injectable, CanActivate, ExecutionContext, UnauthorizedException } from '@nestjs/common';

@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    const token = request.headers.authorization?.split(' ')[1];
    
    if (!token) throw new UnauthorizedException('No token');
    // Verify token...
    return true;
  }
}
```

**Interceptor example:**
```typescript
// logging.interceptor.ts
import { Injectable, NestInterceptor, ExecutionContext, CallHandler } from '@nestjs/common';
import { Observable } from 'rxjs';
import { tap } from 'rxjs/operators';

@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const req = context.switchToHttp().getRequest();
    const start = Date.now();
    
    return next
      .handle()
      .pipe(
        tap(() => {
          const duration = Date.now() - start;
          console.log(`${req.method} ${req.url} - ${duration}ms`);
        }),
      );
  }
}
```

### Database Integration: TypeORM, Prisma, Repository Pattern

NestJS doesn't mandate an ORM; TypeORM and Prisma are most common for PostgreSQL.

#### TypeORM (NestJS-native)
```typescript
// entities/user.entity.ts
import { Entity, PrimaryGeneratedColumn, Column, CreateDateColumn } from 'typeorm';

@Entity('users')  // Table name
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  name: string;

  @Column({ unique: true })
  email: string;

  @Column({ type: 'enum', enum: ['admin', 'user'], default: 'user' })
  role: string;

  @CreateDateColumn()
  createdAt: Date;
}
```

```typescript
// users.module.ts
import { TypeOrmModule } from '@nestjs/typeorm';

@Module({
  imports: [TypeOrmModule.forFeature([User])],  // Register entity
  controllers: [UsersController],
  providers: [UsersService],
})
export class UsersModule {}
```

```typescript
// users.service.ts (repository pattern)
@Injectable()
export class UsersService {
  constructor(
    @InjectRepository(User)
    private readonly usersRepository: Repository<User>,
  ) {}

  async findOne(id: number) {
    return this.usersRepository.findOneBy({ id });  // SELECT * FROM users WHERE id = ?
  }

  async create(createUserDto: CreateUserDto) {
    const user = this.usersRepository.create(createUserDto);  // Create instance
    return this.usersRepository.save(user);                    // INSERT
  }
}
```

#### Prisma (alternative, increasingly popular)
Prisma is a modern ORM with a type-safe query builder. Similar to TypeORM but cleaner API.

```prisma
// schema.prisma
model User {
  id    Int     @id @default(autoincrement())
  name  String
  email String  @unique
  role  String  @default("user")
  createdAt DateTime @default(now())
}
```

```typescript
// users.service.ts (with Prisma)
@Injectable()
export class UsersService {
  constructor(private readonly prisma: PrismaService) {}

  async findOne(id: number) {
    return this.prisma.user.findUnique({ where: { id } });
  }

  async create(createUserDto: CreateUserDto) {
    return this.prisma.user.create({ data: createUserDto });
  }
}
```

**You'll see both in the wild.** TypeORM is more mature; Prisma is more developer-friendly.

#### Repository Pattern
A repository is a class that encapsulates database queries. It decouples services from the ORM.

```typescript
// users.repository.ts (optional, but good practice)
@Injectable()
export class UsersRepository {
  constructor(
    @InjectRepository(User)
    private readonly typeOrmRepository: Repository<User>,
  ) {}

  async findById(id: number): Promise<User> {
    return this.typeOrmRepository.findOneBy({ id });
  }

  async findByEmail(email: string): Promise<User> {
    return this.typeOrmRepository.findOneBy({ email });
  }

  async save(user: User): Promise<User> {
    return this.typeOrmRepository.save(user);
  }
}

// users.service.ts
@Injectable()
export class UsersService {
  constructor(private readonly usersRepository: UsersRepository) {}

  async findOne(id: number) {
    return this.usersRepository.findById(id);
  }
}
```

**Why:** Easier to test (mock the repository); easier to swap databases later; single place to change queries.

### Testing: Unit vs E2E

#### Unit Testing (services in isolation)
```typescript
// users.service.spec.ts
describe('UsersService', () => {
  let service: UsersService;
  let repository: Repository<User>;

  beforeEach(async () => {
    const module: TestingModule = await Test.createTestingModule({
      providers: [
        UsersService,
        {
          provide: getRepositoryToken(User),
          useValue: { findOneBy: jest.fn(), save: jest.fn() },
        },
      ],
    }).compile();

    service = module.get<UsersService>(UsersService);
    repository = module.get<Repository<User>>(getRepositoryToken(User));
  });

  it('should find a user by id', async () => {
    const user = { id: 1, name: 'John' };
    jest.spyOn(repository, 'findOneBy').mockResolvedValue(user);

    const result = await service.findOne(1);
    expect(result).toEqual(user);
    expect(repository.findOneBy).toHaveBeenCalledWith({ id: 1 });
  });
});
```

#### E2E Testing (full integration)
```typescript
// users.e2e-spec.ts
describe('Users (e2e)', () => {
  let app: INestApplication;

  beforeAll(async () => {
    const module: TestingModule = await Test.createTestingModule({
      imports: [AppModule],  // Full app
    }).compile();

    app = module.createNestApplication();
    await app.init();
  });

  it('GET /users should return all users', async () => {
    return request(app.getHttpServer())
      .get('/users')
      .expect(200)
      .expect((res) => {
        expect(Array.isArray(res.body)).toBe(true);
      });
  });

  it('POST /users should create a user', async () => {
    return request(app.getHttpServer())
      .post('/users')
      .send({ name: 'John', email: 'john@example.com', role: 'user' })
      .expect(201)
      .expect((res) => {
        expect(res.body.id).toBeDefined();
      });
  });
});
```

**Tools:** Jest (included with `@nestjs/testing`), Supertest for HTTP assertions.

### How a Mobile Engineer Contributes

You won't architect the backend. You'll **add features** to an existing NestJS app. Common tasks:

#### 1. Add a new endpoint to an existing module
```typescript
// In the controller:
@Post('bulk')
@UseGuards(AuthGuard)
async bulkCreate(@Body() createUserDtos: CreateUserDto[]) {
  return this.usersService.bulkCreate(createUserDtos);
}

// In the service:
async bulkCreate(createUserDtos: CreateUserDto[]) {
  const users = this.usersRepository.create(createUserDtos);
  return this.usersRepository.save(users);
}
```

#### 2. Add validation to a DTO
```typescript
// Update the DTO:
export class CreateUserDto {
  @IsString()
  @MinLength(3)
  @MaxLength(50)
  name: string;

  @IsEmail()
  email: string;

  @IsEnum(UserRole)
  role: UserRole;

  @IsPhoneNumber('VN')  // class-validator has country-specific rules
  phone: string;
}
```

#### 3. Add a guard (permission check)
```typescript
// role.guard.ts
@Injectable()
export class RoleGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const requiredRole = this.reflector.get<string>('role', context.getHandler());
    if (!requiredRole) return true;

    const request = context.switchToHttp().getRequest();
    const userRole = request.user?.role;
    return userRole === requiredRole;
  }
}

// Use it:
@Delete(':id')
@SetMetadata('role', 'admin')
@UseGuards(RoleGuard)
async delete(@Param('id') id: string) {
  return this.usersService.delete(+id);
}
```

#### 4. Fix a slow query
```typescript
// Before (slow):
async findAll() {
  return this.usersRepository.find();  // Loads ALL users
}

// After (fast):
async findAll(page = 1, limit = 20) {
  const skip = (page - 1) * limit;
  return this.usersRepository.find({
    skip,
    take: limit,
    order: { createdAt: 'DESC' },
  });
}
```

#### 5. Add a test for a service method
```typescript
// In the .spec.ts file:
it('should return paginated users', async () => {
  const users = [{ id: 1, name: 'John' }, { id: 2, name: 'Jane' }];
  jest.spyOn(repository, 'find').mockResolvedValue(users);

  const result = await service.findAll(1, 20);
  expect(result).toEqual(users);
  expect(repository.find).toHaveBeenCalledWith({
    skip: 0,
    take: 20,
    order: { createdAt: 'DESC' },
  });
});
```

### NestJS vs Express: What Transfers, What Doesn't

| Concept | Express | NestJS | Transfers? |
|---------|---------|--------|---|
| HTTP methods (@Get, etc.) | `app.get()`, `router.post()` | `@Get()`, `@Post()` decorators | Mostly yes (different syntax) |
| Middleware | `app.use()` | `@Injectable()` with NestMiddleware | Yes (NestJS middleware is Express middleware) |
| Routes | Flat per-file | Organized per module | No (restructure thinking) |
| Database queries | Manual (e.g., `db.query()`) | ORM with repositories | Depends on your Express setup |
| Error handling | `try/catch`, next(err) | Filters, exception classes | Similar concept, different API |
| Testing | `supertest` + mocks | `@nestjs/testing` + mocks | Similar tools, different setup |
| Async/Promises | Yes (`async/await`) | Yes (`async/await`) | Full transfer |
| TypeScript | Optional | Required | Full transfer (you already use TS) |
| Authorization | Middleware + manual checks | Guards + decorators | Cleaner in NestJS |

**Your advantage:** You know Express and async JavaScript. The module/DI system is new, but the HTTP concepts are the same.

### Quick Reference: Minimal Controller → Service → Module

```typescript
// user.entity.ts
@Entity('users')
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  name: string;
}

// create-user.dto.ts
export class CreateUserDto {
  @IsString() name: string;
}

// users.service.ts
@Injectable()
export class UsersService {
  constructor(
    @InjectRepository(User)
    private repo: Repository<User>,
  ) {}

  async findAll() {
    return this.repo.find();
  }

  async create(dto: CreateUserDto) {
    return this.repo.save(this.repo.create(dto));
  }
}

// users.controller.ts
@Controller('users')
export class UsersController {
  constructor(private service: UsersService) {}

  @Get()
  findAll() {
    return this.service.findAll();
  }

  @Post()
  create(@Body() dto: CreateUserDto) {
    return this.service.create(dto);
  }
}

// users.module.ts
@Module({
  imports: [TypeOrmModule.forFeature([User])],
  controllers: [UsersController],
  providers: [UsersService],
  exports: [UsersService],
})
export class UsersModule {}
```

**Same endpoint in Express for comparison:**
```typescript
const router = express.Router();

router.get('/users', async (req, res) => {
  try {
    const users = await db.query('SELECT * FROM users');
    res.json(users);
  } catch (err) {
    res.status(500).json({ message: err.message });
  }
});

router.post('/users', async (req, res) => {
  try {
    const { name } = req.body;
    if (!name) return res.status(400).json({ message: 'Name required' });
    const result = await db.query('INSERT INTO users (name) VALUES ($1)', [name]);
    res.status(201).json(result);
  } catch (err) {
    res.status(500).json({ message: err.message });
  }
});

app.use('/users', router);
```

### NestJS Caveats & Common Pitfalls

1. **TypeORM lazy loading:** By default, related entities aren't loaded. Use `leftJoinAndSelect()` or relations to avoid N+1 queries.
2. **Circular dependencies:** Module A imports Module B, Module B imports Module A → NestJS fails. Use `forwardRef()` to break the cycle.
3. **Global guards:** Applied to every route (including health checks, metrics). Be careful with `@UseGuards()` globally.
4. **Async initialization:** Services that need async setup (e.g., database connection) use `onModuleInit()`.
5. **Testing:** Mocking nested dependencies can be verbose. Use factories and test modules to simplify.

# AWS/GCP Cloud-Native & Serverless for Mobile Engineers

## I. What "Cloud-Native" Actually Means (Not Marketing)

**Core principle:** let the cloud vendor handle the **operations**, you handle the **logic**.

**Four concrete shifts:**

| Your mindset | Cloud-native mindset |
|---|---|
| "I own a server; I must patch, scale, monitor, back up the OS" | "I use a managed service; the vendor owns patches, backups, scaling — I own the API contract" |
| "State lives on the machine; I must manage it" | "Stateless; state lives in a database or cache the vendor operates" |
| "Scale = bigger machine (vertical)" | "Scale = more copies running in parallel (horizontal); the load balancer routes requests" |
| "Configuration is in a file on the server" | "Configuration is in environment variables, secrets vaults, or a declarative IaC file" |
| "I SSH into the machine to debug" | "I read logs and traces in a managed dashboard; machines are immutable" |

**Why this matters for Glory's cash-handling software:** Retail banks deploy your mobile app + backend worldwide. Scaling to 1,000 simultaneous users and then to 10,000 must be **automatic**, not manual. Your backend must stay up while you sleep — managed services give you that.

## II. The AWS Primitives You'll Touch

### A. Computing: Lambda vs. ECS/Fargate vs. EC2

**What he knows from LocalStack + Heroku/Firebase:**
- LocalStack lets you emulate AWS SQS and DynamoDB locally — you've seen the AWS API shape.
- Heroku abstracts away the server entirely (you `git push`, it runs).
- Firebase (Google) abstracts away the server entirely (you call an API, it runs).

**What those do NOT teach:**
- AWS's real pricing model (pay-per-invocation for Lambda; pay-per-hour for compute).
- Cold starts (Lambda takes ~1-3s on first call after idle; a running container doesn't).
- Deployment mechanics (Heroku pushes code; AWS Lambda requires a ZIP or OCI image).

**Three choices: which do I pick?**

| Choice | What it is | Use it when | Do NOT use it when |
|---|---|---|---|
| **Lambda** | Managed serverless function. You upload code (Node.js, Python, Java, Go, etc.). Vendor runs it, charges on memory x duration (billed per ms). | API endpoints (short-lived, <15min), background jobs, webhooks, scheduled tasks (cron). Startup time ≤1s matters. Cost-predictable (pay-per-call). | Long-running work (video encoding, complex compute) — Lambda has a **15-minute timeout hard limit**. High-traffic endpoints that need sub-100ms latency consistently — Lambda cold starts add 1-3s. |
| **ECS/Fargate** | Managed containers. You give a Docker image. Vendor runs it on servers you don't see. Pay per second. | Long-running services (your Node.js API server). Flexible timeout (hours if you want). Predictable, continuous workload. | Single-use scripts. If you only need something to run once a day for 1 second, Lambda is cheaper. |
| **EC2** | Unmanaged VM. You SSH, patch the OS, manage the network, scale manually. | Almost never. (You still **might** if you need GPU or specialized hardware.) | Everything else. GSV should not use this. |

**Glory's likely choice: ECS/Fargate + RDS PostgreSQL for the backend. Lambda for scheduled background jobs (e.g., clean up old payment records).**

### B. Storage: S3 (Object), RDS (Relational Database)

**S3 — Object storage (files)**
- Used for: receipts, images, documents, static website assets, backups, video clips.
- You **do not** SSH into S3; you `PUT`/`GET` via HTTPS.
- Pricing: per GB stored + per million requests.
- Durability: 11 nines (99.999999999% — if a data center burns, AWS keeps your data).
- Integration with mobile: **pre-signed URLs** — your backend generates a time-limited URL (valid for 1 hour) that your mobile app uses to `PUT` a photo directly to S3 without storing the AWS credential in the app.

**What Duong knows:** nothing. **What transfers:** he's used file uploads to backend APIs (Express) and Firebase Storage. The pattern is similar: app → credential → storage. Pre-signed URLs are a *way* to do that securely without shipping the credential.

**RDS — Managed PostgreSQL/MySQL/MariaDB**
- AWS runs the database. You connect via hostname/username/password (like any Postgres). AWS handles backups, failover, patches.
- Pricing: per instance type per hour (e.g., `db.t3.small` = ~$0.05/hr).
- **Multi-AZ** (availability zones): AWS replicates your data to another data center; if one burns, traffic switches automatically. Recommended for production.
- Backup: automatic daily snapshots kept for 7 days; restore to any point-in-time.

**What Duong knows:** PostgreSQL itself (Express + HapiJS + Supabase Postgres on Space360). What he does NOT know: AWS-specific operations — how RDS failover works, how to resize the instance, how to monitor slow queries via CloudWatch. These are tutorials, not conceptual gaps.

**When NOT to use RDS: you need a document database (DynamoDB), a cache (ElastiCache), or a search engine (Elasticsearch).** Glory uses PostgreSQL, so RDS is the right choice.

### C. Networking: API Gateway, Load Balancer, VPC

**API Gateway**
- Sits in front of your Lambda or backend service.
- Handles API versioning, rate limiting, CORS, API keys, WAF (web application firewall).
- Converts HTTPS requests to Lambda invocations (or sends them to ECS).
- Pricing: per 1 million requests.

**Load Balancer (ALB — Application Load Balancer)**
- Sits in front of your ECS services.
- Routes requests to multiple running containers.
- Health checks: if a container crashes, ALB removes it from rotation and starts a new one.
- Sticky sessions: if your app needs a user's request to land on the same container (e.g., in-memory session state), you can configure this — but cloud-native apps avoid in-memory state.

**VPC (Virtual Private Cloud)**
- Your isolated network inside AWS.
- RDS runs inside the VPC, not on the public internet.
- ECS tasks run inside the VPC.
- API Gateway sits on the public internet and talks to your VPC.
- This is **default and invisible** — you do not need to configure VPC for Glory's first sprint. But know that your database is **not** publicly reachable; it's inside the VPC, and only your backend services can reach it.

### D. Secrets, Authentication, Monitoring

**Secrets Manager** — stores API keys, database passwords, SSH private keys.
- Single source of truth. If you rotate a password, all apps pick up the new one.
- Integrates with RDS: RDS can auto-rotate the master password monthly.
- Pricing: $0.40/secret/month + per-rotation.

**IAM (Identity & Access Management)** — who can do what.
- Role: "what permissions do I have?" e.g., "ECS task role can read RDS, write S3, call Secrets Manager."
- Policy: the JSON document listing those permissions.
- **Principle of least privilege:** your mobile app does **not** have AWS credentials. Your backend has an IAM role. Your backend calls AWS APIs with that role.

**Cognito (Identity Provider)** — handles user sign-up, login, MFA, social login (Google, Facebook, Apple).
- Mobile app signs in via Cognito.
- Cognito returns a JWT access token.
- Mobile app sends that token in the Authorization header to your backend.
- Your backend validates the token (without calling Cognito each time — JWT is self-signed by Cognito).
- Pricing: per 50,000 monthly active users, then $0.015 per additional 1,000.

**What Duong knows:** OAuth 2.0 multi-social SSO (he built it). JWT. What he does NOT know: Cognito as a service (vs. rolling it himself). Cognito is the "managed" version; it saves you from building sign-up validation, email verification, password reset, MFA, rotation, etc. It's a *specialization* of OAuth 2.0, not a new concept.

**CloudWatch** — logs, metrics, dashboards.
- Every AWS service logs to CloudWatch.
- You query logs: `fields @timestamp, @message | filter @message like /error/ | stats count()`.
- Metrics: CPU, memory, request count, latency, errors.
- Alarms: "if error rate > 1% for 5 minutes, page the on-call engineer."

**What Duong knows:** none of this. **What transfers:** he's used Jenkins (CI/CD) and SonarQube (code quality). CloudWatch is AWS's version of "here's what's happening in production." The concepts are the same; the tool is different.

## IV. Serverless Deep Dive: Lambda and Cloud Functions

### A. What Happens When You Call Lambda

```
1. Mobile app → API Gateway
2. API Gateway → Lambda (first invocation)
3. AWS boots a container, runs your code (cold start: 1-3s)
4. Your code returns JSON
5. API Gateway → Mobile app response

Next invocation (within ~15 min):
1. Mobile app → API Gateway
2. API Gateway → Lambda (second invocation, warm)
3. Container already running, no boot (warm start: <100ms)
4. Your code returns JSON
```

**Cold start factors:**
- **Language:** Node.js is fast (~500ms); Python is slower (~1-2s); Java is slowest (~3s).
- **Package size:** larger ZIP = slower boot.
- **VPC:** if your Lambda is inside a VPC (to reach RDS), VPC setup adds ~1s.
- **Runtime:** Node.js 20 is faster than Node.js 14.

**Execution limits:**
- **Timeout:** 15 minutes **hard limit**. If your function takes >15 min, it dies.
- **Memory:** 128 MB to 10,240 MB. More memory = more CPU (AWS scales them together).
- **Ephemeral storage:** 512 MB temporary `/tmp`. If you need more (video encoding), use S3.
- **Concurrency:** default 1,000 concurrent Lambdas per account per region.

**Pricing model:**
- Cost model: **allocated memory x execution duration**, billed per millisecond, plus a per-request charge. (Deliberately no rate quoted here - never quote a cloud price from memory in an interview.)
- 1 million free calls per month (generous for startups).
- To reason about it out loud: *"a million short calls a month at a small memory setting is cents rather than dollars, but I would check current pricing rather than quote a figure."*
- **Compare to ECS/Fargate:** `db.t3.small` RDS + 1 Fargate task = ~$50-80/month minimum, regardless of traffic.

**Decision:** Lambda is cheap for low-traffic APIs (e.g., webhooks, background jobs). ECS/Fargate is better if your API runs continuously.

### B. Cold Starts — How to Minimize Them

**Bad:** every Lambda invocation cold-starts because traffic is sporadic.
- Solution: **provisioned concurrency** — pay to keep N containers warm. Expensive.

**Good:** your Lambda warms up naturally because traffic is consistent (>1 invocation every 5 minutes).
- Solution: do nothing. CloudWatch metrics tell you if you're warm or cold.

**Better:** use **Cloud Run** (GCP) or **Fargate** instead.
- Container stays running; no cold start.
- Better for: long-running APIs, human-facing endpoints where <1s matters.

## V. Async Messaging: SQS, SNS, Pub/Sub

**Why:** sometimes you can't process a request immediately.

**Example:** user hits "send SMS to 100 customers."
- Sync approach: API waits for all 100 SMSes to send (30s+). User gets a timeout. Bad.
- Async approach: API accepts the job, returns immediately. Backend job processes 100 SMSes in the background. User gets a webhook/email when done.

**SQS (AWS Simple Queue Service)**
- Producer: puts messages in a queue.
- Consumer: polls the queue, processes messages, deletes them.
- Useful for: decoupling a frontend action from a backend job.
- Example: mobile app → API → SQS → Lambda processes in background.

**SNS (AWS Simple Notification Service)**
- Producer: publishes a message to a "topic."
- Subscribers: multiple consumers can subscribe to the topic.
- Example: order placed → SNS topic → email service, SMS service, Slack service all triggered.

**GCP Pub/Sub** — same concept as SNS.

**What Duong knows:** LocalStack emulating SQS. He hasn't built with it, but he's seen the API. Real AWS SQS works the same way — pull messages, process, delete.

## VII. File Uploads: Pre-Signed URLs

**Insecure approach:**
```javascript
// DON'T DO THIS
const s3Creds = require('./s3-key.json'); // AWS key in your app
// Ship the key in your app → hackers get the key
```

**Secure approach (pre-signed URLs):**
```javascript
// Backend (Node.js)
const AWS = require('aws-sdk');
const s3 = new AWS.S3();

app.post('/receipt-upload-url', (req, res) => {
  const url = s3.getSignedUrl('putObject', {
    Bucket: 'glory-receipts',
    Key: `receipts/${Date.now()}.pdf`,
    Expires: 3600, // valid for 1 hour
  });
  res.json({ uploadUrl: url });
});
```

```javascript
// Mobile app (React Native)
const response = await fetch('https://api.glory.com/receipt-upload-url', {
  method: 'POST',
  headers: { Authorization: `Bearer ${token}` },
});
const { uploadUrl } = await response.json();

// Now upload directly to S3 using the pre-signed URL
await fetch(uploadUrl, {
  method: 'PUT',
  body: receiptPDF,
  headers: { 'Content-Type': 'application/pdf' },
});
```

**Why this works:**
- AWS credential is **never** in the mobile app.
- Backend issues a time-limited token (1 hour).
- Mobile app uses the token to upload directly to S3.
- After 1 hour, the URL expires.
- Hacker stealing the URL from network traffic can only upload for 1 hour.

**What Duong knows:** Supabase Storage has a similar pattern (generate a signed URL for uploads). Same concept, different service.

## VIII. The Gap: NestJS

**He knows:** Express (2018-2020), HapiJS (university).
**He doesn't know:** NestJS.

**What NestJS is:** a **framework** on top of Express/Fastify that adds structure (similar to Spring in Java).

**Honest line for the interview:**
> "I've built Node.js APIs with Express and HapiJS, so I understand middleware, routing, and async patterns. I haven't used NestJS specifically, but I've read the docs and understand it's a structured framework built on Express — dependency injection, decorators, TypeScript-first. I'm confident I'd ramp up quickly; my first sprint would be studying their tutorial and doing a code review with the team."

**1-2 day tutorial to understand NestJS:**
- NestJS uses **decorators** (TypeScript's `@` syntax) to mark controllers, services, middleware.
- **Dependency injection:** the framework injects dependencies into constructors (you don't manually create objects).
- Example:
  ```typescript
  @Controller('/receipts')
  export class ReceiptsController {
    constructor(private readonly receiptsService: ReceiptsService) {}
    
    @Post()
    async create(@Body() dto: CreateReceiptDto) {
      return this.receiptsService.create(dto);
    }
  }
  
  @Injectable()
  export class ReceiptsService {
    constructor(private readonly db: DatabaseService) {}
    
    async create(dto: CreateReceiptDto) {
      return this.db.receipts.insert(dto);
    }
  }
  ```

This is **not** magic; it's just structured boilerplate that forces you to separate concerns (controller = routing, service = business logic, database = persistence). Express requires the same separation but doesn't enforce it — you write it manually.

## IX. The Other Gap: OWASP vs. ISO 27001

**What he has:** ISO/IEC 27001:2022 ISMS (governance, access control, incident management, risk assessment).
**What he lacks:** OWASP hands-on application testing.

**OWASP top 10 (2021) — quick summary:**

| Risk | What it means | How to avoid it |
|---|---|---|
| Injection (SQL, NoSQL, command) | Attacker sends `'; DROP TABLE users; --` in a form field. | Use parameterized queries (e.g., prepared statements). Never concatenate user input into SQL. |
| Broken authentication | Weak password reset, session hijacking, brute force. | Use Cognito/Auth0 (don't roll your own). Enforce MFA. Rate-limit login attempts. |
| Sensitive data exposure | Passwords stored in plain text, PII logged, HTTPS disabled. | Hash passwords (bcrypt, Argon2). Encrypt PII at rest and in transit. Use HTTPS. |
| XML external entity (XXE) | Attacker sends malicious XML that reads `/etc/passwd`. | Disable XML external entity parsing. Use JSON instead of XML. |
| Broken access control | User A can access User B's data by guessing the ID. | Verify the user owns the resource before returning it. Use IAM roles. |
| Security misconfiguration | Debug mode enabled in production, default credentials, unnecessary services running. | Disable debug mode. Use Secrets Manager for credentials. Review cloud IAM policies. |
| Cross-site scripting (XSS) | Attacker injects `<script>` tags into a web page. | Escape user input in HTML context. Use Content Security Policy (CSP). |
| Insecure deserialization | Attacker sends malicious serialized object; code deserializes it and runs arbitrary code. | Avoid deserializing untrusted data. Use JSON, not pickle/native serialization. |
| Using components with known vulnerabilities | Old npm package with a published CVE. | `npm audit`. Pin versions. Use a private registry with SBOM scanning. |
| Insufficient logging & monitoring | Attacker breaks in, no one notices for 3 months. | Log security events (login, data access, API key rotation). Set CloudWatch alarms. |

**What Duong should say:**

I haven't done formal OWASP penetration testing, but I understand the top 10 and apply them in code review: parameterized queries, use managed auth (Cognito), encrypt sensitive data, follow least-privilege in IAM. **Data flow: user uploads a receipt**

5. S3 event → Lambda → update RDS (receipt processing status).
6. Lambda → SNS → push notification to mobile app ("Receipt processed").

**What Duong needs to know for an architecture conversation:**
- Why ECS/Fargate (not Lambda) for the main API: it's long-running, continuous, predictable load.
- Why Lambda for the background job: short-lived, triggered by S3 event, no need to keep a container warm.
- Why pre-signed URLs for upload: no AWS credentials in the app, time-limited, direct to S3 (no backend bandwidth).
- Why RDS inside VPC: database is not publicly reachable; only ECS services can reach it.
- Why SNS for notifications: one publish → multiple subscribers (email, SMS, push, Slack).

## XI. Multi-Region and Disaster Recovery (First Sprint? No. Eventually.)

**Challenge:** a cash-handling app must work in Vietnam, Japan, and Singapore. If AWS us-east-1 goes down, your Vietnam deployment still needs to work.

**Options:**
1. **Same region, multi-AZ:** RDS replicates to another availability zone in the same region. If one AZ fails, AWS fails over automatically. Failover time: AWS states "as quickly as 60 seconds"; realistically 1-2 minutes for standard Multi-AZ (under ~35s for the Multi-AZ cluster variant with two readable standbys). Replication lag: <1s.
2. **Multi-region:** database replicas in multiple regions. Deployment time: <1 min. Replication lag: up to a few seconds (eventually consistent).
3. **Read replicas + write to primary:** a common pattern. Reads go to the nearest replica; writes go to the primary and replicate async.

**For Glory's first sprint:** stick to single region (ap-southeast-1, Singapore or ap-northeast-1, Tokyo), multi-AZ RDS. This is 80% of disaster recovery benefit for 20% of the complexity cost.

# OAuth 2.0, OIDC, Certificate Security & OWASP — Mobile Engineer Interview Prep

## OAuth 2.0: The correct mental model

**Not** a single protocol; a **delegation framework** (RFC 6749, 2012). The candidate is the **Resource Owner**; the mobile app is the **Client** (public client, no secret); GLORY's backend is the **Resource Server**; GLORY's auth system is the **Authorization Server**.

### Grant Types: what still matters for mobile

| Grant Type | Use Case | Why deprecated for mobile |
|---|---|---|
| **Authorization Code + PKCE** | Mobile native apps, SPAs | CORRECT for React Native. PKCE (RFC 7636) is mandatory for public clients. |
| Implicit (`response_type=token`) | Browser SPA (2010s) | Deprecated 2019 (OAuth 2.0 Security Best Practices); tokens in URL fragment = leakable. |
| Password (`username` + `password`) | Legacy, trusted clients | Deprecated; exposes credentials to the app. GLORY will not accept this. |
| Client Credentials | Backend-to-backend auth | Not applicable for user login. |
| Device Flow | Smart TVs, IoT | Not applicable; designed for input-constrained devices. |

### Authorization Code + PKCE: the correct mobile flow

```
1. App generates:
   code_verifier = random 128-byte string (base64url-encoded)
   code_challenge = SHA256(code_verifier) base64url

2. App opens browser (SFSafariViewController / Chrome Custom Tab):
   /authorize?
     client_id=<ID>
     redirect_uri=<your-app://callback>
     response_type=code
     code_challenge=<SHA256 hash>
     code_challenge_method=S256
     scope=openid profile email
     nonce=<random, for OIDC>
     state=<random>

3. User authenticates on the backend's login page
   Authorization Server returns: redirect_uri?code=<code>&state=<state>

4. App (only the app, NOT the browser) exchanges:
   POST /token:
     grant_type=authorization_code
     code=<code>
     client_id=<ID>
     code_verifier=<original, unhashed>
     redirect_uri=<must match step 2>
```

**Why PKCE is mandatory:** Without it, if an attacker intercepts the authorization code, they can exchange it for a token (no secret to verify ownership). PKCE binds the code to the original device via the code_verifier, which only the app knows.

**Why `state` is mandatory:** CSRF protection. Authorization Server must verify that the state returned matches the state the app sent. Store state in memory during the flow.

**Why `nonce` is mandatory (OIDC only):** Replay attack protection on the ID token. Authorization Server includes the nonce in the ID token; app must verify it matches.

## Access tokens vs Refresh tokens

| Property | Access Token | Refresh Token |
|---|---|---|
| **Lifetime** | Short (5–15 min typical) | Long (days to months) |
| **Use** | Authenticate API requests (`Authorization: Bearer <access_token>`) | Obtain a new access token when the old one expires |
| **Storage on mobile** | Keychain (iOS) / Keystore (Android); rotate aggressively | Keychain / Keystore; store securely; rotate on refresh |
| **Revocation** | Fast (short TTL); server can blacklist in-flight | Slower; requires coordination; a breach is more damaging |
| **Refresh-token rotation** | N/A | **SHOULD rotate on every use (best practice, not an RFC 6749 mandate)** (RFC 6749 Section 6; mitigates token theft) |
| **Reuse detection** | N/A | On refresh, return a NEW refresh token and retire the old one; if the client submits an old token again, it indicates a compromise (token was stolen and replayed) |

### Your production investigation: HttpOnly cookies vs Bearer tokens on mobile

**HttpOnly cookies** (server-side session storage):
- Server sets `Set-Cookie: session=<token>; HttpOnly; Secure; SameSite=Strict` in response headers.
- Browser/WebView automatically attaches the cookie to every request.
- JavaScript **cannot** access the cookie (HttpOnly blocks `document.cookie`).
- **Mobile RN problem:** React Native's Fetch API and axios do NOT automatically manage cookies the way a browser does. You must:
  - Use a custom HTTP client that tracks cookies (e.g., `react-native-http-client`, `expo-fetch` with cookie jar).
  - Or: explicitly handle the Set-Cookie header and store the session token securely.

**Bearer tokens** (client-side storage):
- Client receives a token: `{"access_token": "...", "refresh_token": "..."}`
- Client stores the access token in Keychain/Keystore.
- Client attaches it to every API call: `Authorization: Bearer <access_token>`
- Server validates the token (signature, expiration, etc.).
- **Mobile-native:** This is the standard OAuth 2.0 pattern for mobile apps. No cookie-jar complexity.

**Your anchor (turn into this story):** "I investigated an OAuth refresh-token flow delivered over HttpOnly cookies in a production React Native app. The issue: RN's Fetch doesn't automatically track Set-Cookie headers the way a browser does. I built a curl test matrix to isolate the problem—testing how the auth server issued cookies, how the RN client parsed Set-Cookie headers, and how the backend session store validated them. The solution: switch to bearer tokens (access + refresh) stored in Keychain, with refresh-token rotation on every use. This eliminated the cookie-jar complexity and aligned with OAuth 2.0 mobile best practices."

**For a cash-handling-machine company:** Bearer tokens + signed JWTs are auditable, comply with ISO 27001 (you log every token issue, expiration, rotation), and are easier to integrate with device certificates (mTLS, device pinning).

## Token storage on mobile: Keychain vs Keystore vs AsyncStorage

| Storage | iOS | Android | Encrypted by default | Use case | Why NOT AsyncStorage |
|---|---|---|---|---|---|
| **Keychain** | ✅ Native | ❌ | ✅ (device-level encryption) | Store access/refresh tokens | AsyncStorage is plain-text / easily serialized JSON |
| **Keystore** | ❌ | ✅ Native | ✅ (device-level encryption) | Store access/refresh tokens | AsyncStorage offers no encryption, no device-level protection |
| **AsyncStorage** | ✅ (RN API) | ✅ (RN API) | ❌ Unencrypted | Non-sensitive app state (UI preferences, cached data) | **Tokens in AsyncStorage = CRITICAL BUG.** On a compromised device or rooted phone, AsyncStorage is readable by any app. |
| **SecureStore** / **Encrypt** libraries | ✅ wrapper | ✅ wrapper | Depends on implementation | Fallback if Keychain/Keystore unavailable | Slower, redundant if Keychain/Keystore work |

**React Native packages:**
- `react-native-keychain` (iOS Keychain + Android Keystore)
- `react-native-secure-storage` (alternative, wider Android support)
- `expo-secure-store` (if using Expo; manages Keychain/Keystore under the hood)

**Code smell:** If you see `AsyncStorage.setItem('access_token', token)` in the codebase, flag it immediately. This is a security vulnerability.

## Refresh-token rotation and reuse detection

**Rotation (mandatory for every refresh):**
```
Client sends: POST /token
  grant_type=refresh_token
  refresh_token=<old_refresh_token>

Server responds:
  {
    "access_token": "<new_short-lived>",
    "refresh_token": "<new_refresh_token>",  ← Different from old one
    "expires_in": 900
  }

Client:
  - Stores new refresh token in Keychain
  - DELETES the old refresh token
```

**Reuse detection (optional but recommended):**
```
Server tracks: for each refresh_token, what was the previous refresh_token?
On POST /token:
  if (submitted_refresh_token != current_valid_token) {
    AND (submitted_refresh_token == previous_token) {
      → Token was replayed (old token resubmitted)
      → This indicates the token was leaked/stolen
      → Revoke entire session; require user re-login
    }
  }
```

**Your story (tie to production investigation):** "In the refresh-token flow investigation, we found that without rotation, a stolen refresh token could be used indefinitely. With rotation, each exchange issues a new token and invalidates the old one. If an attacker tries to use a token we've already rotated past, we catch it and revoke the session."

## OIDC: Identity layer on top of OAuth 2.0

**OAuth 2.0 = authorization** (does this user have permission to access resource X?).
**OIDC = authentication + identity** (who is this user?).

OIDC is a thin wrapper (RFC 6749 + RFC 6750 + OIDC Core). It adds:
- **ID token** (a JWT signed by the Authorization Server).
- **UserInfo endpoint** (request `GET /userinfo` with access token; returns claims like `sub`, `name`, `email`).
- **Discovery document** (`/.well-known/openid-configuration`; lists endpoints, key URLs, etc.).

### ID token (a JWT)

```
eyJhbGciOiJSUzI1NiIsImtpZCI6IjEifQ.eyJpc3MiOiJodHRwczovL2V4YW1wbGUuY29tIiwic3ViIjoiMTIzNDU2Nzg5MCIsImF1ZCI6ImNsaWVudElEIiwiZXhwIjoxNjIzMDU2NDA0LCJpYXQiOjE2MjMwNTI4MDQsIm5vbmNlIjoiYWJjMTIzIiwibmFtZSI6IkpvaG4gRG9lIn0.SIGNATURE
```

**Decoded claims:**
```
{
  "iss": "https://example.com",          ← Issuer (must match Authorization Server)
  "sub": "1234567890",                   ← Subject (user ID)
  "aud": "clientID",                     ← Audience (must match your client_id)
  "exp": 1623056404,                     ← Expiration (UTC timestamp)
  "iat": 1623052804,                     ← Issued at
  "nonce": "abc123",                     ← Must match nonce from step 1 (replay protection)
  "name": "John Doe"                     ← Custom claims
}
```

### JWT validation (in code, NOT just eyeballing it)

```javascript
// Pseudocode: never skip validation
const jwt = require('jsonwebtoken');
const jwksClient = require('jwks-rsa');

const client = jwksClient({
  jwksUri: 'https://example.com/.well-known/jwks.json'  // Fetch public keys
});

function getKey(header, callback) {
  client.getSigningKey(header.kid, (err, key) => {
    if (err) callback(err);
    const signingKey = key.getPublicKey();
    callback(null, signingKey);
  });
}

jwt.verify(idToken, getKey, {
  algorithms: ['RS256'],  // Only accept RS256; reject 'none', 'HS256' (alg confusion)
  issuer: 'https://example.com',  // Verify iss claim
  audience: 'clientID',  // Verify aud claim
  nonce: nonceFromStep1  // Verify nonce claim
}, (err, decoded) => {
  if (err) throw new Error(`Token validation failed: ${err.message}`);
  // Token is valid; decoded.sub is the user ID
});
```

**Alg confusion attack (critical):** If the Authorization Server is misconfigured to accept the `none` algorithm or the client doesn't enforce an algorithm, an attacker can forge a token. Always:
- Whitelist `algorithms: ['RS256']` (or the server's specific algorithm).
- Reject `'none'` and `'HS256'` unless you control the server's secret.

### JWKS and key rotation

The Authorization Server publishes its public keys at `/.well-known/jwks.json`:
```json
{
  "keys": [
    {
      "kty": "RSA",
      "kid": "1",  ← Key ID (matches JWT header "kid")
      "use": "sig",
      "n": "...",  ← Modulus
      "e": "AQAB"  ← Exponent
    },
    {
      "kty": "RSA",
      "kid": "2",  ← Newer key
      "use": "sig",
      "n": "...",
      "e": "AQAB"
    }
  ]
}
```

When you receive a JWT:
1. Read `header.kid` (e.g., `"1"`).
2. Fetch JWKS and find the key with matching `kid`.
3. Use that key's public key to verify the JWT signature.

**Key rotation:** Server can rotate keys (issue new tokens with a new `kid`). Your client must fetch JWKS dynamically and cache it (with a short TTL, e.g., 1 hour).

### OIDC discovery document

```
GET /.well-known/openid-configuration

{
  "issuer": "https://example.com",
  "authorization_endpoint": "https://example.com/authorize",
  "token_endpoint": "https://example.com/token",
  "userinfo_endpoint": "https://example.com/userinfo",
  "jwks_uri": "https://example.com/.well-known/jwks.json",
  "response_types_supported": ["code", "token", "id_token", ...],
  "scopes_supported": ["openid", "profile", "email", ...],
  ...
}
```

Parse this on app startup to avoid hardcoding URLs. If GLORY's auth service ever changes endpoints, your app adapts automatically.

## Certificate-based security: TLS, mTLS, pinning

### TLS (Transport Layer Security)

Mobile app → GLORY backend: HTTPS = TLS 1.3 (mandatory).
- Server presents a certificate (signed by a trusted CA).
- Client verifies the certificate chain and the domain name.
- A symmetric key is negotiated; all traffic is encrypted.

**Standard TLS:** Client trusts any certificate signed by a system-trusted CA (Apple's root store on iOS, Android's root store on Android).

### Mutual TLS (mTLS / certificate pinning)

Instead of trusting all CA-signed certs, the client **trusts only specific certificates** (pinned).

**Why a cash-handling-machine company cares:**
- Each device (cash recycler) has a certificate issued by GLORY.
- The backend only communicates with devices whose certificate is pinned.
- An attacker who intercepts HTTPS traffic with a different (valid CA-signed) certificate will fail the pin check.

**Implementation on React Native:**

```javascript
// Using Fetch with mTLS (requires native module or third-party library)
// react-native-ssl-pinning or axios with custom transport

import { fetch as pinnedFetch } from 'react-native-ssl-pinning';

const response = await pinnedFetch('https://api.glory.example.com/data', {
  method: 'GET',
  sslPinning: {
    certs: ['cert1', 'cert2'],  // Base64-encoded certificate data
  },
  headers: {
    'Authorization': `Bearer ${accessToken}`
  }
});
```

**Alternative (TrustKit):**
```javascript
import TrustKit from 'react-native-trustkit';

TrustKit.setConfig({
  domainPinningPolicy: {
    'api.glory.example.com': {
      includeSubdomains: false,
      enforcePinning: true,
      disableDefaultReportUri: true,
      pins: [
        'sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=',  // Public key hash
      ]
    }
  }
});
```

### Operational risk of certificate pinning

**If the certificate expires and you didn't update the app:**
- All API calls fail (hard fail; users are blocked).
- You must force an app update, which takes days (app store review).

**Mitigation:**
- Pin multiple certificates (current + next-rotation).
- Implement a fallback: if pinning fails, allow user to retry with standard TLS (accept the risk).
- Use certificate pinning only for the backend API, not for third-party services.
- **Communicate with GLORY's ops team:** when do they plan to rotate the device certificates? Plan your app release around it.

# React Native + Expo: Senior Architecture & Performance Deep Dive

## React Native New Architecture — The Shift from Bridge to JSI

### The Problem: The Old Bridge
- **JavaScript runs on a separate thread** from native (Android's Java thread, iOS's Objective-C runtime).
- Every call from JS to native (and back) crosses the **serialization bridge**: JS object → JSON → C++ → native code.
- Serialization is **synchronous, blocking, and lossy** — you cannot pass function pointers or complex objects directly.
- The JS thread polls the native queue; you cannot interrupt JS execution from native.
- **Result:** latency, animations stutter when JS is busy, no way to run high-frequency updates (e.g., scroll events) on the native thread.

### JSI: JavaScript Interface
- **Direct memory pointers** between JS and native — no serialization.
- Native modules can expose **host objects** (C++ objects with JS properties and methods).
- JS can hold a reference to a native function and **call it directly** without crossing the bridge.
- **Synchronous** — JS waits for the native call; native can wait for JS.
- **Example:** Reanimated 2 uses JSI to run animation worklets directly on the native UI thread, bypassing the bridge entirely.
- **Not a framework** — a lower-level capability that frameworks (Fabric, TurboModules) build on top of.

### Fabric: The New Renderer
- **Old:** UIManager serializes JS style changes → bridge → native layout engine → screen. Many frames are dropped.
- **New:** Fabric is a **C++ rendering engine** that RN JS talks to via JSI (no bridge).
- **Committed trees:** Fabric operates on a committed tree (shadow tree) on the JS thread, then pushes a diff to the UI thread. No serialization between trees.
- **Concurrent rendering:** JS can prepare the next frame while the UI thread is rendering the current one.
- **Fabric and the New Architecture are ENABLED BY DEFAULT as of RN 0.76** (Oct 2024). Not all third-party libraries support it yet, but an interoperability layer provides backward compatibility; you can opt out with `newArchEnabled=false`.
  - Core components in new arch: `<View>`, `<Text>`, `<Image>`, `<ScrollView>`, `<FlatList>` — mostly stable.
  - Custom native components: need TurboModules + Codegen to work with Fabric.
  - Third-party libraries: check for `"fabric"` in the package.json or GitHub.
- **Performance gain:** startup is ~10% faster, scroll smoother, animations don't drop frames when JS is busy.

### TurboModules: Native Modules on JSI
- **Old:** NativeModules.XYZ crosses the bridge for every call.
- **New:** TurboModules are defined in a type-safe generated interface. JSI connection is set up at app launch, then direct calls.
- **Lazy initialization:** A TurboModule is only instantiated when first accessed — not all at startup.
- **Example structure:**
  ```typescript
  // Android/iOS native code (Kotlin/Swift)
  package com.example.myapp
  
  // The bridge is gone; you implement a single interface per platform.
  // Codegen generates the JSI glue.
  ```
- **How it changes native module work:**
  - You define the API in a **Spec** (TypeScript-like interface in the `android/` or `ios/` directory).
  - Codegen (part of RN build) reads the Spec and generates:
    - Android: Java/Kotlin boilerplate linking the Spec to your native code.
    - iOS: Objective-C++ boilerplate linking to your native code.
  - You implement the native side (e.g., `VideoPlayer.java`), implementing the interface Codegen created.
  - No more `@ReactMethod` annotations or manual serialization.

### Codegen
- **Input:** TypeScript interfaces describing your native module's API.
- **Output:** Platform-specific boilerplate (Android, iOS) that links the Spec to native code.
- Example Spec file (`android/src/main/java/com/example/myapp/VideoPlayerSpec.ts`):
  ```typescript
  export interface Spec extends TurboModule {
    play(id: string): Promise<void>;
    pause(id: string): Promise<void>;
    getDuration(id: string): Promise<number>;
  }
  ```
- Codegen runs at build time; you never manually write the JSI boilerplate.
- **Type safety:** The generated code enforces that JS can only call methods with the right signatures.

### Hermes: The JavaScript Engine
- **What is it:** Meta's JavaScript engine optimized for mobile (not V8).
- **Why:** V8 is built for server-side performance; Hermes prioritizes **startup time and memory footprint**.
- **Key features:**
  - **Bytecode compilation:** Hermes compiles to bytecode during the RN build; the app ships bytecode, not source. Faster startup, smaller download.
  - **Lazy evaluation:** Functions are parsed only when called (not upfront).
  - **Garbage collection:** Optimized for mobile (smaller heap, shorter pause times).
- **Current status (RN 0.76):** Hermes is the default on iOS (since 0.64) and Android (since 0.73). V8 is opt-in for comparison.
- **Performance:** ~50% faster startup on Android, ~10% on iOS, ~20% smaller bundle.
- **Trade-off:** Hermes doesn't support some ES2015+ features (e.g., `Proxy`, `WeakMap`). If you use them, RN will error at build time.

### Putting It Together: New Architecture Flow
```
JS Code
  ↓
JSI (direct memory pointers, no serialization)
  ↓
Fabric (C++ renderer on UI thread)
  ↓
TurboModules (native code via Codegen)
  ↓
Native (Kotlin/Java, Swift)

Hermes compiles all of this at build time to bytecode.
```

## Expo: Managed → Bare Is Dead. Prebuild + CNG Is Real.

### The Old Frame (Obsolete)
- "Managed" = Expo services host your build; you push JS, they build the binary.
- "Bare" = You own the native `android/` and `ios/` folders; Expo is just an SDK.
- **This distinction is meaningless now.** Both Managed and Bare apps use the same codebase and tooling.

### What Changed: Prebuild & Continuous Native Generation
- **Prebuild (`eas build --platform android --build-profile preview`):**
  - You run a command; EAS generates `android/` and `ios/` folders from your config on their servers.
  - You get a signed APK or IPA. The generated native code is stable, reproducible, and versioned.
  - You can download the generated code, inspect it, and commit it if you want.
- **Continuous Native Generation (CNG):**
  - Same as prebuild, but the generated code is ephemeral — you don't commit it.
  - The config (`app.json`, config plugins) is the source of truth.
  - Build happens on EAS, not locally.
  - **Duong's experience:** He uses EAS Build/Submit. CNG is the modern default.
- **When to commit native code:**
  - If you modify the generated `android/` or `ios/` directly (e.g., for a one-off fix), commit it.
  - If you're scripting the build locally (CI/CD), you may want to commit the generated code to ensure reproducibility.
  - In general: prefer keeping native code generated, not committed. It's cleaner and safer.

### Config Plugins: Customization Without Forking
- **Problem:** You need to add native code (e.g., permissions, native module initialization) without managing `android/` and `ios/`.
- **Solution:** Config plugins run during prebuild and modify the native code before it's compiled.
- **Example:** Adding camera permissions.
  ```json
  {
    "plugins": [
      ["expo-camera", { "cameraPermission": "Allow MyApp to access your camera" }]
    ]
  }
  ```
- **How it works:** The plugin is a JavaScript function that receives the native config, modifies it (e.g., adds to `AndroidManifest.xml`), and returns it. Prebuild runs all plugins, generates the modified native code, and builds.
- **Writing a custom plugin:** You can write your own if you need non-standard native setup.
  ```javascript
  const withCustomPermissions = (config) => {
    return withAndroidManifest(config, async (config) => {
      // Modify config.android.manifest
      return config;
    });
  };
  ```

### Dev Client: Local Debugging
- **Old:** You run `expo start` on your machine; the device talks to your machine's dev server via LAN or tunnel.
- **New (Dev Client):** You build a dev version of the app (with native debugging libraries baked in) and install it on your device. The app talks to your local dev server directly.
- **Why it matters:** You can test native code changes locally without rebuilding the app every time.
- **When to use it:**
  - You're writing a native module or config plugin.
  - You're debugging a production crash that only happens in release builds.
  - You want to test with the exact native configuration you'll ship.
- **How:** `eas build --platform android --profile development --local` (or similar).

### EAS Build: Deterministic Builds on Managed Infrastructure
- **What:** You push your code; EAS builds the APK/IPA on their servers (not your machine).
- **Why:** Consistent, reproducible builds (same OS, same toolchain, every time). No "works on my machine" issues.
- **Versioning:** You specify a target EAS SDK version (`expo@50`); that version has tested versions of Android build tools, Xcode, Node, etc.
- **iOS signing:** EAS handles provisioning profiles and certificates (or you can bring your own).
- **Build profiles:** Define per-environment (development, preview, production).
  ```json
  {
    "build": {
      "preview": { "ios": { "autoIncrement": "buildNumber" } },
      "production": { "distribution": "app-store" }
    }
  }
  ```

### EAS Update: Over-the-Air (OTA) Updates
- **What it changes:** You can push JS + asset updates without going through the store.
- **Constraints (critical for interviews):**
  - **Only JS and assets.** You cannot change native code or permissions over OTA.
  - **Not a full app replacement.** OTA patches the bundle (JavaScript and images); native libraries stay the same.
  - **Runtime version must match.** If you bump Expo SDK or a native dependency, you must also bump `runtimeVersion`. Old app versions will not accept OTA updates for a new runtime.
- **Example workflow:**
  ```bash
  # Fix a bug, commit.
  eas update --channel production --message "Fixed login bug"
  # App downloads and installs the new bundle; no store review, no wait.
  ```
- **Staged rollout:** Roll out to 5% of users, monitor, then 100%. EAS handles this.
- **Downtime risk:** If your OTA update has a crash, you can publish a new OTA update within minutes. But there's a gap (seconds to minutes) where some users hit the buggy version.

### Why Expo (Answering the Skeptic)
- **Developer velocity:** Prebuild + config plugins + EAS Update let you iterate fast. No Xcode or Android Studio.
- **Managed testing:** Expo maintains the compatibility between RN, Expo SDK, native tools, and peer dependencies. You don't.
- **One codebase:** Same code runs on both iOS and Android (with platform-specific tweaks via config plugins).
- **"But it's locked in."** Not anymore. If you need custom native code, write a config plugin or bare workflow. You're not locked; you're choosing a default that works until it doesn't.
- **"But it adds overhead."** Expo SDK is a small layer on top of RN. The binary size difference is negligible now (same ASM in both).
- **Duong's honest take:** "We ship two products on Expo + Prebuild. We can fix a bug and push to users in minutes without store review. For our team's size and velocity, that's invaluable."

## Performance: What Seniors Get Asked

### Startup / Time to Interactive (TTI)
- **What's slow:** JS thread initializing, bundle parsing, requiring modules, running top-level effects, rendering the first screen.
- **Profiling tools:**
  - iOS: Xcode Instruments (Time Profiler, System Trace).
  - Android: Android Studio Profiler (CPU, Memory, Frames).
  - RN CLI: `react-native run-android --profile` builds a release APK with profiling enabled.
- **Common wins (in order of impact):**
  1. **Hermes bytecode:** Automatic if Hermes is enabled; saves ~50% startup on Android.
  2. **Lazy require:** Don't require modules at the top level if they're not needed immediately.
     ```javascript
     // Before (slow):
     const HeavyLib = require('./HeavyLib');
     
     // After (fast):
     const getHeavyLib = () => require('./HeavyLib');
     // Call getHeavyLib() when you actually need it.
     ```
  3. **Split bundle:** Code-split at the navigator level. EAS and Metro support this.
  4. **Reduce initial render:** Render a splash screen, then lazily load the home screen.
- **Measurement:** `react-native-performance` or `react-native-trace-update` for frame-level metrics.

### Bundle Size
- **Factors:**
  - RN core: ~1.2 MB uncompressed (most of it is bridge/VM code). App Store compression brings it to ~300 KB.
  - Expo SDK: ~500 KB to 1 MB (varies with modules you enable).
  - Your code: typically 100 KB to 500 KB.
  - Dependencies: can balloon (e.g., `moment` + 10 other libs = easily 2 MB).
- **Wins:**
  1. **Dependencies audit:** `npm list --all` or `yarn workspaces info`. Look for duplicates and alternatives.
     - Replace `moment` with `date-fns` (100 KB → 20 KB).
     - Replace `lodash` with `lodash-es` and use tree-shaking.
  2. **Dynamic imports:** Only require dependencies when used.
     ```javascript
     // Only import when needed.
     const Analytics = () => import('./Analytics');
     ```
  3. **Hermes:** Reduces bundle size by ~10-20% via bytecode and stripping.
  4. **Flipper / EAS Insights:** Use EAS's bundle analyzer to see which modules are largest.

### Re-render Control: Memoization and Keys
- **Problem:** A parent re-renders → all children re-render, even if their props didn't change.
- **React.memo:** Wrap a child component to skip re-renders if props are identical.
  ```javascript
  const UserCard = React.memo(({ user, onPress }) => (
    <View onPress={onPress}><Text>{user.name}</Text></View>
  ));
  // Re-renders only if `user` or `onPress` changes.
  ```
- **useMemo:** Memoize expensive calculations.
  ```javascript
  const expensiveValue = useMemo(() => {
    return expensiveCompute(data);
  }, [data]); // Recompute only if `data` changes.
  ```
- **useCallback:** Memoize a function reference so child components can compare it.
  ```javascript
  const handlePress = useCallback(() => {
    dispatch(action);
  }, [dispatch]);
  
  return <Button onPress={handlePress} />;
  // Button's onPress reference is stable; Button won't re-render unless something else changes.
  ```
- **FlatList keys:** Always provide a **unique, stable key** for each item.
  ```javascript
  <FlatList
    data={items}
    keyExtractor={(item) => item.id} // Not the index!
    renderItem={({ item }) => <ItemCard item={item} />}
  />
  ```
  If you use the index as a key and the list is reordered, FlatList will re-render every item.

### FlatList vs FlashList
- **FlatList (React Native core):**
  - **Virtualization:** Only renders visible items + a buffer.
  - **Performance:** Good for lists with <1000 items or static lists.
  - **Limitations:** Cell recycling can cause visual glitches if not careful (e.g., if you cache state inside a cell component).
- **FlashList (Shopify):**
  - **Better virtualization:** More aggressive, renders fewer off-screen items.
  - **Autosizing:** Automatically handles variable-height items.
  - **Performance:** Smoother scrolling, faster scroll-to-top on large lists (>1000 items).
  - **Caveat:** Not in RN core; you manage it separately. Config plugin available for Expo.
- **When to use FlashList:** Lists with >1000 items, variable heights, smooth scroll performance is critical.
- **When FlatList is enough:** Small to medium lists, mostly stable heights.
- **Duong's experience:** He shipped apps with both; FlashList is the safer choice for large lists.

### Reanimated Worklets and the UI Thread
- **Problem:** JavaScript runs on a thread separate from the native UI thread. If JS is busy, animations stutter.
- **Reanimated solution:** Run animation logic (e.g., scroll position → transform) on the **native UI thread**, not JS.
- **Worklets:** A function marked with `worklet` runs on the UI thread via JSI.
  ```javascript
  import Reanimated, {
    useSharedValue,
    useAnimatedStyle,
    withSpring,
    runOnJS,
  } from 'react-native-reanimated';
  
  const animated = useSharedValue(0);
  
  const animatedStyle = useAnimatedStyle(() => ({
    transform: [{ scale: animated.value }],
    // This runs on the UI thread, even if JS is busy.
  }));
  
  const handlePress = () => {
    animated.value = withSpring(1, { damping: 2 });
  };
  
  return (
    <Reanimated.View style={[styles.box, animatedStyle]} onPress={handlePress} />
  );
  ```
- **runOnJS:** Call a JS function from a worklet (e.g., to trigger a navigation or state change).
  ```javascript
  animated.value = withSpring(1, { damping: 2 }, () => {
    runOnJS(navigation.navigate)('NextScreen');
  });
  ```
- **Performance gain:** Smooth 60 FPS animations even when JS is blocked by heavy computation.

### Hermes Bytecode
- **How it works:** Your JS source is compiled to bytecode during the Expo build. The app ships `.hbc` files, not `.js`.
- **What bytecode saves:**
  - Startup: No JS parsing, just load and run bytecode. ~50% faster on Android.
  - Memory: Bytecode is denser than source.
  - Source hiding: Bytecode is not human-readable (obfuscation side effect).
- **Trade-off:** Bytecode is version-specific. If you change Hermes, you must rebuild.
- **Source maps:** Stack traces still point to original source files (EAS provides source maps for crash monitoring).

## Navigation with Expo Router

### File-Based Routing
- **How it works:** File structure mirrors URL structure.
  ```
  app/
    (auth)/
      login.tsx
      signup.tsx
    (tabs)/
      home.tsx
      profile.tsx
      settings.tsx
    index.tsx
  ```
  Routes: `/`, `/login`, `/signup`, `/home`, `/profile`, `/settings`.
- **Benefits:**
  - Routes are co-located with components.
  - Type-safe deep linking (TypeScript knows all valid routes).
  - Code splitting (each route can be a separate bundle).

### Typed Routes (with Expo Router v2+)
- **Automatic type generation:** Expo Router reads your file structure and generates a TypeScript type `Href`.
- **Benefit:** Mistyped route names are caught at compile time.
  ```typescript
  // Correctly typed:
  navigation.navigate('profile', { id: 123 });
  
  // Would error:
  navigation.navigate('profie'); // Typo caught by TS.
  ```

### Deep Linking
- **Setup in `app.json`:**
  ```json
  {
    "scheme": "myapp",
    "plugins": [
      ["expo-router", {
        "origin": "https://myapp.com"
      }]
    ]
  }
  ```
- **Matching:** `myapp://profile/123` → routes to `profile.tsx` with params `{ id: 123 }`.
- **Web:** `https://myapp.com/profile/123` → same route.
- **Integration with social login:** After OAuth callback, redirect to `myapp://home`; Expo Router handles the navigation.

### Dynamic Segments
- `app/profile/[id].tsx` → matches `/profile/123`, `/profile/456`, etc.
- Access params via `useLocalSearchParams()`:
  ```typescript
  const { id } = useLocalSearchParams();
  ```
- Optional: `[id]?` matches both `/profile` and `/profile/123`.

## State Management: Trade-offs

### Server-State vs Client-State
- **Server-state:** Data from your backend (user list, posts, etc.). **Rarely changes on its own; the server is the source of truth.** Problem: you fetch it, it may become stale while the user is offline.
- **Client-state:** UI state (is the modal open? which tab is active?). **Controlled by the user.** Doesn't need to sync with the server.
- **Wrong tool for the job:** Using Redux (client-state optimized) for server-state leads to over-fetching, over-normalizing, and stale data.

### Redux (Client-State Focused)
- **When:** Deeply nested component tree, complex client-state mutations.
- **Example:** Form state across multiple steps, drag-drop UI state.
- **Trade-off:** Boilerplate (reducers, actions, dispatch). Overkill for most mobile apps now.
- **Duong's experience:** He's shipped Redux. It works, but modern alternatives are lighter.

### Zustand (Lightweight Client-State)
- **Philosophy:** Minimalist. One file, one store, no reducers.
  ```typescript
  import { create } from 'zustand';
  
  const useStore = create((set) => ({
    count: 0,
    increment: () => set((state) => ({ count: state.count + 1 })),
  }));
  ```
- **Benefit:** Small bundle size, simple API, fast enough for most apps.
- **When:** UI state, local mutations, simple shared state.

### React Query (TanStack Query) — Server-State Focused
- **Philosophy:** Server data should be cached, invalidated intelligently, and synced with the backend.
  ```typescript
  const { data: users, isLoading, refetch } = useQuery({
    queryKey: ['users'],
    queryFn: async () => {
      const res = await fetch('/api/users');
      return res.json();
    },
    staleTime: 5 * 60 * 1000, // 5 minutes
  });
  ```
- **Key features:**
  - **Stale-while-revalidate:** Data is "stale" after 5 min, but the user sees the stale data while a fresh fetch happens in the background.
  - **Automatic invalidation:** When you post data, React Query can invalidate the cache automatically.
  - **Deduplication:** Multiple components querying the same data share one request.
  - **Offline support:** Queries are retried when the app comes back online.
- **Benefit:** Dramatically less boilerplate than Redux + API calls.
- **Duong's experience:** He's used React Query (`react-query` in Expo projects). It's standard now for server-state.

### How to Choose
1. **Server-state (user list, posts, profile)?** → React Query.
2. **Client-state (form, modal open/close)?** → Zustand or `useState`.
3. **Complex state machines (multi-step wizard)?** → Zustand + a state machine library like `xstate`, or just useReducer.
4. **Deeply nested tree with many consumers of the same state?** → React Context + Zustand (Context as the provider, Zustand as the store).

## Offline-First & Cache Invalidation

### Why It Matters
- Mobile apps lose connectivity. Graceful degradation is not optional.
- Users expect to read cached data offline.
- Users expect to post data; it should sync when connectivity returns.

### Cache Patterns
- **Read-through:** Fetch from cache first; if miss, fetch from server.
- **Stale-while-revalidate:** Serve cached data immediately; refresh in the background.
  ```typescript
  const { data } = useQuery({
    queryKey: ['posts'],
    queryFn: fetchPosts,
    staleTime: 5 * 60 * 1000, // After 5 min, marked stale.
    gcTime: 10 * 60 * 1000, // After 10 min of not being used, garbage collect.
  });
  // App shows cached posts immediately; React Query fetches fresh ones in background.
  ```
- **Optimistic updates:** User posts a comment; immediately show it in the UI (optimistic), then confirm with the server.
  ```typescript
  const mutation = useMutation({
    mutationFn: postComment,
    onMutate: async (newComment) => {
      // Optimistically update cache
      await queryClient.cancelQueries({ queryKey: ['comments'] });
      const prev = queryClient.getQueryData(['comments']);
      queryClient.setQueryData(['comments'], (old) => [
        ...old,
        { ...newComment, id: Math.random() }, // Temp ID
      ]);
      return { prev }; // For rollback
    },
    onError: (err, newComment, context) => {
      // Rollback on error
      queryClient.setQueryData(['comments'], context.prev);
    },
  });
  ```

### Cache Invalidation Strategy
- **Time-based:** Mark data stale after N seconds (e.g., user list after 5 min).
- **Event-based:** After a POST/PUT, invalidate related queries.
  ```typescript
  mutation.mutate(newData, {
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['posts'] });
      // React Query will re-fetch posts in the background.
    },
  });
  ```
- **Manual:** Call `refetch()` when the user pulls to refresh.

## Native Modules: When and How

### When You Actually Need One
- **Audio playback** with custom controls (not just play/pause; e.g., pitch shifting).
- **Camera** beyond the stock Expo camera (e.g., custom frame processing).
- **Platform-specific APIs** (e.g., NFC on Android).
- **Performance-critical loops** (real-time speech recognition, high-frequency sensor data).
- **Not necessary:** Most integrations (payment, analytics, ads) have RN libraries via Expo or npm.

### Old Bridge (Deprecated)
- Write a native class (Java/Swift).
- Expose methods with `@ReactMethod` annotation.
- Call from JS: `NativeModules.MyModule.doSomething()`.
- **Problem:** Every call serializes arguments, crosses the bridge, deserializes result. Slow and lossy.

### TurboModules (New Way)
- **Spec:** Define your API in TypeScript.
  ```typescript
  // native/VideoPlayer/VideoPlayerSpec.ts
  import type { TurboModule } from 'react-native';
  import { TurboModuleRegistry } from 'react-native';
  
  export interface Spec extends TurboModule {
    play(id: string): Promise<void>;
    pause(id: string): Promise<void>;
    getDuration(id: string): Promise<number>;
  }
  
  export default TurboModuleRegistry.getEnforced<Spec>('VideoPlayer');
  ```
- **Codegen:** Expo's build process (via `eas build`) reads the Spec and generates boilerplate.
- **Native:** You implement the interface.
  - Android: `VideoPlayer.kt` extending the generated base.
  - iOS: `VideoPlayer.swift` extending the generated base.
- **Benefit:** Type-safe, no manual serialization, JSI speeds things up, and Fabric-compatible.

### Decision Tree
- **Is it performance-critical or real-time?** → TurboModule.
- **Does it need native sensors/hardware?** → TurboModule.
- **Is there a good Expo plugin already?** → Use it (e.g., `expo-camera`, `expo-audio`).
- **Do you need one for a startup scenario or edge case?** → First, try Expo plugins or npm libraries. Only roll your own if you've exhausted those.

## Release Engineering: OTA, Versioning, Staged Rollouts

### EAS Update (Over-the-Air)
- **What it does:** Push JS + assets updates without store review.
- **What it cannot do:**
  - Change native code.
  - Add new permissions (requires store review).
  - Update Expo SDK version (requires new build).
  - Update native dependencies (requires new build).
- **How:**
  ```bash
  eas update --channel production --message "Fixed bug in login"
  ```
  App users check for updates in the background; if available, download and install.

### CodePush (Alternative to EAS Update)
- **Microsoft's service** for RN OTA updates.
- **How it works:** Similar to EAS Update but with different hosting and CLI.
- **Caveat:** Duong has used CodePush on a previous project. Both EAS Update and CodePush have similar constraints (JS only, no native changes).

### Stallion (Custom OTA)
- **Duong has integrated this.** A self-hosted OTA solution.
- **Benefit:** Full control over the update server.
- **Caveat:** You manage the server, versioning, and device rollout logic.

### Runtime Version
- **Problem:** If you upgrade Expo SDK or a native dependency, old app versions cannot use the new OTA updates.
- **Solution:** Increment `runtimeVersion` in `app.json`.
  ```json
  {
    "runtimeVersion": "1.0.0",
    "plugins": ["expo-router", ...]
  }
  ```
- **How EAS Update uses it:** Only apps with matching `runtimeVersion` download the update. Old versions don't break.
- **In practice:**
  - You ship app v1 with `runtimeVersion: "1.0.0"`.
  - You push 5 OTA updates (JS fixes). All use `runtimeVersion: "1.0.0"`.
  - You upgrade Expo SDK. You bump `runtimeVersion: "1.1.0"` and rebuild the app.
  - Only new installs and old versions that update will get `1.1.0` updates. Older app versions stay on `1.0.0` updates.

### Store Constraints
- **iOS:** App Store review (~48 hours). New permissions, new native code, updated Expo SDK all require review.
- **Android:** Google Play review (~1-2 hours). Same constraints as iOS, but faster.
- **OTA updates (JS only):** No review. 15-30 min to reach users.
- **Strategy:** Bug fixes and feature flagged features → OTA. New permissions or major version bumps → store review (plan ahead).

### Staged Rollout
- **EAS Update supports this.**
  ```bash
  eas update --channel production --rollout 0.05
  # 5% of users get the update first.
  # After 1 hour (or you manually), bump to 0.20, then 1.0.
  ```
- **Benefit:** If the update crashes, only 5% of users are affected. You can roll back and fix in <1 hour.

### Versioning Strategy
- **app.json `version` (iOS/Android store):** `"1.2.3"`. Increment for store releases.
- **Build number (`buildNumber`):** Incremented for every EAS Build, even if the version doesn't change.
- **`runtimeVersion`:** Incremented when native code or Expo SDK changes.
- **`expo.version` (legacy):** Ignore; use `version` instead.

### Crash Monitoring & Source Maps
- **How crashes are reported:** An uncaught error in JS crashes the app. The OS sends a crash report to your server (if you set it up).
- **The problem:** Minified/bytecode stack traces don't point to your source.
- **Solution:** Upload source maps to your crash monitoring service.
- **EAS Integration:**
  ```bash
  eas build --platform android --auto-submit
  # After a build, EAS automatically uploads source maps to your monitoring service (if configured).
  ```
- **Manual:** After a build, download the source map from EAS and upload to Sentry/Rollbar/etc.

## Testing React Native Realistically

### React Native Testing Library
- **Philosophy:** Test behavior, not implementation details.
- **Example:**

1. **Business logic:** Always. Edge cases matter.

5. **Styling:** No. Visual regression is caught by screenshots.

## Architecture Decisions: The Questions a Lead Reasons About

### Navigation: Context + Expo Router, or Redux + React Navigation?
**Scenario:** User logs in → navigate to home. But the app is deep in a nested stack. How do you navigate out?

**Old way (React Navigation + Redux):**
```typescript
dispatch(setUser(user));
navigation.navigate('RootStack', {
  screen: 'Home',
  // Deep linking gets complex fast.
});
```

**Expo Router way:**
```typescript
// File structure is the navigation structure.
// After login, you set a global state (e.g., user is logged in).
// App's root dynamically switches between (auth) and (tabs) based on that state.
// Expo Router handles all navigation, even deep linking, automatically.
```

**Answer:** "Expo Router handles the routing structure; a lightweight client-state store (Zustand) manages whether the user is logged in. No Redux needed. Simpler, less boilerplate, and deep linking works for free."

### Bundle Size: Should We Code-Split?
**Scenario:** App has a huge dashboard screen (10 screens worth of code). Loading it on app startup slows TTI.

**Options:**
1. Ship everything in one bundle. Fast lookup, but slow startup.
2. Code-split: Home screen loads immediately, dashboard loads on-demand.

**Trade-off:**
- Code-splitting saves startup time but adds latency when the user navigates to the dashboard.
- If the dashboard is rarely used: code-split. If it's accessed in the first 30 sec: don't split.

**Answer:** "Measure first. Profile the app with `react-native run-android --profile`. If startup is >3 sec, code-split. Otherwise, the overhead of multiple bundles isn't worth it."

### State Management: React Query + Zustand, or Redux?
**Scenario:** You have user profile data, posts (server state), and form UI state (client state). The form needs to read the user's data.

**Redux approach:**
```typescript
const formData = useSelector(state => state.form);
const user = useSelector(state => state.user); // Manually cached
const dispatch = useDispatch();
```

**React Query + Zustand approach:**
```typescript
const { data: user } = useQuery(['user']); // Automatic caching + sync
const formData = useStore(state => state.form); // Client state
```

**Answer:** "React Query owns server-state sync; Zustand owns client state. Separation of concerns. Less boilerplate, automatic cache invalidation. Redux is overkill unless you have deeply nested state mutations."

### OTA Updates: When to Push vs. Store Review?
**Scenario:** You fixed a critical login bug. Users are stuck. Do you push an OTA update or wait for store review?

**Decision tree:**
- Bug only affects JS (e.g., validation logic)? → OTA, 15 min to users.
- Bug requires new permissions? → Store review, 48 hours.
- Bug is in native code? → Store review.
- Workaround exists (e.g., user can retry)? → Store review; no rush.

**Answer:** "OTA for JS bugs, store review for native/permission changes. Critical bugs (users can't log in) justify bypassing staged rollout and going 100% immediately, but always have a rollback plan."

### Offline Support: What Should Work?
**Scenario:** User opens the app, there's no connectivity. What should they see?

**Approach:**
- Cached data (old posts, user profile) → show immediately.
- New data (real-time notifications)? → show stale cached data with a "Syncing..." indicator.
- User posts a comment offline? → queue it, sync when online.
- Queued actions fail after coming online? → show retry UI.

**Implementation:**
```typescript
// Use React Query's `refetchOnReconnect` and `refetchOnWindowFocus`.
const { data, refetch, isRefetching } = useQuery({
  queryKey: ['posts'],
  queryFn: fetchPosts,
  refetchOnReconnect: true,
  staleTime: 5 * 60 * 1000,
});

// For mutations, queue them if offline.
const mutation = useMutation({
  mutationFn: postComment,
  onError: (err) => {
    if (err.message === 'Network unavailable') {
      // Queue for retry later.
      queueMutation('postComment', args);
    }
  },
});
```

**Answer:** "Cache everything that's not real-time. Optimistically update the UI. Queue mutations. Automatically retry when connectivity returns. Users shouldn't be blocked by network."

#### Schema & Index Basics (Repeat This)
**When interviewer asks "Tell me about your Postgres experience":**

> "I've designed schemas for the Space360 property management app — entities for users, properties, bookings. I use surrogate keys (id SERIAL/BIGSERIAL), foreign keys with ON DELETE CASCADE for orphan prevention, check constraints for data integrity. Standard normalization: users table, properties table with user_id FK, bookings with both user and property FKs. I'm familiar with SERIAL vs BIGSERIAL (32-bit vs 64-bit sequence) — SERIAL is fine for small tables, BIGSERIAL when you risk overflow. I use NOT NULL constraints on required fields and defaults (created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP)."

**B-tree indexes and when they matter:**
- B-tree is Postgres's default index type — used for `=`, `<`, `>`, range queries
- Non-B-tree: GiST (geometric), GIN (full-text, arrays), BRIN (big sequential tables), Hash (equality only)
- Indexes speed **WHERE** and **JOIN ON** conditions; they slow **INSERT/UPDATE** (index maintenance)
- An index is not used if:
  - The column is wrapped in a function: `WHERE UPPER(email) = 'X'` doesn't use index on `email` (but `email = LOWER('X')` does)
  - Type mismatch: `WHERE id = '123'` (string) vs column `id INTEGER` may or may not use index depending on planner
  - Selectivity is bad: `WHERE is_deleted = false` on a table 99% non-deleted may be seqscan faster than index
  - LIMIT is large: `SELECT * FROM users LIMIT 1000000` will seqscan; indexes help only on small LIMIT + WHERE

#### EXPLAIN and ANALYZE (Concrete)
```sql
EXPLAIN (ANALYZE, BUFFERS) 
SELECT users.id, COUNT(*) as booking_count 
FROM users 
LEFT JOIN bookings ON users.id = bookings.user_id 
WHERE users.created_at > NOW() - INTERVAL '30 days' 
GROUP BY users.id;
```

**Read the output (left to right):**
- `Seq Scan on users` = sequential scan (full table read) — if cost is high and WHERE is selective, create an index: `CREATE INDEX idx_users_created ON users(created_at);`
- Cost format: `cost=start..end` = planner's guess for startup + total CPU cost (not real time)
- `Actual time=start..end` = real milliseconds when you run ANALYZE
- `Buffers: shared hit X read Y` = cache hits vs disk reads — if read is high, table might not fit in `shared_buffers` (default 128MB; production 25% of RAM)
- `Rows: X` estimate vs actual — planner wrong? Statistics might be stale; run `ANALYZE table_name;`

**Your honest line if asked about query optimization at scale:**
> "I've used EXPLAIN and ANALYZE to find slow queries — identifying missing indexes, N+1 problems in application code. I've looked at Postgres stats to understand table size and cache hit ratios. I haven't tuned Postgres internals like shared_buffers or work_mem in production, but I understand the tradeoffs: bigger cache = faster reads, but more RAM consumed."

#### N+1 Query Problem
**What it is:** `for user in users: print(user.bookings)` — one query for users, then N queries for each user's bookings = N+1 total

**Fix in application code:** JOIN + GROUP BY (what Postgres does efficiently) or batch load
```javascript
// BAD (N+1 in Node.js + Postgres)
const users = await db.query('SELECT * FROM users WHERE created_at > NOW() - INTERVAL 30 DAYS');
for (const user of users.rows) {
  const bookings = await db.query('SELECT * FROM bookings WHERE user_id = $1', [user.id]); // repeated per user
  user.bookings = bookings.rows;
}

// GOOD (one query, let DB join)
const result = await db.query(`
  SELECT users.*, json_agg(json_build_object('id', bookings.id, 'date', bookings.date)) as bookings
  FROM users
  LEFT JOIN bookings ON users.id = bookings.user_id
  WHERE users.created_at > NOW() - INTERVAL '30 days'
  GROUP BY users.id;
`);
```

#### Transactions and Isolation Levels
**Isolation levels (PostgreSQL default: READ COMMITTED):**
- `READ UNCOMMITTED` (Postgres **doesn't support** — same as READ COMMITTED)
- `READ COMMITTED` (default): dirty reads prevented; non-repeatable reads & phantom reads **possible**
  - Safe for: most web apps; each statement sees committed data
  - Problem: if two transactions read the same row, second writer wins (lost update)
- `REPEATABLE READ`: snapshot isolation; sees consistent snapshot from transaction start
  - Safe for: reporting queries, batch operations
  - Caveat: "phantom reads" (new rows inserted by other txns during your txn are visible at your isolation level — Postgres 9.1+ actually prevents phantoms too, so closest to SERIALIZABLE)
- `SERIALIZABLE`: strictest; errors if concurrent txns conflict
  - Safe for: financial transactions, inventory updates
  - Cost: slower; aborts and retries common

**Your concrete line:**
> "On the Space360 platform, most queries run at READ COMMITTED, which is safe for our booking workflow: user reads a property, reads availability, books it. If two users click the same slot, one booking succeeds, the other gets a conflict error that the frontend retries. For the admin dashboard reporting, I've used explicit transaction blocks to ensure read consistency over a 2-second window, which is REPEATABLE READ behavior."

#### Connection Pooling and Serverless Break It
**Why pooling matters:**
- PostgreSQL spawns one backend process per connection; max `max_connections` = ~100-200 typically
- Every application instance opens a connection pool (default 10 connections)
- If 100 app instances × 10 connections each = 1,000 connections needed — Postgres can't handle it
- **Connection pool** (PgBouncer, node-postgres default): app instances hold a pool of reused connections; PgBouncer sits between app and Postgres, multiplexes many app connections into fewer real DB connections

**Serverless breaks naive pooling:**
- AWS Lambda spins up cold (new process, new pool) → fills connection slots fast
- 100 concurrent Lambdas = 100 connections + their pools = exhaustion
- **Fix:** use **PgBouncer in transaction mode** (not session mode) or **RDS Proxy** (AWS's PgBouncer equivalent)
  - Transaction mode: connection returned to pool after each transaction (lower latency, trades isolation)
  - Session mode: connection held for life of client session (safer, not viable for Lambdas)
- On Supabase (what he uses): Supabase handles pooling; just connect normally in Lambda

**Your honest line if asked:**
> "I haven't personally set up a serverless Lambda + Postgres stack in production. But I understand the pooling problem: Lambdas are stateless, so each cold start opens new connections; if you have 100 concurrent Lambdas, you'd exhaust Postgres's connection limit quickly. I know AWS RDS Proxy solves this, and I've seen it documented in my ISO 27001 security training materials — connection pooling is part of capacity planning. On Supabase, it's handled for me."

### Docker: Images, Containers, Layers, and Local Development

#### What You Know
- Docker experience: yes (not elaborated in brief; clarify what he's done)
- Containerized development matters to a team: parity between local and production
- Likely: `docker-compose` for local dev, maybe EAS Build containerization

#### Image vs Container (Repeat This)
- **Image**: blueprint (like a class in OOP) — Dockerfile defines layers, built with `docker build`
- **Container**: running instance (like an object) — `docker run` creates a container from an image
- Images are immutable; containers are ephemeral unless you `docker commit`

#### Dockerfile Layer Caching (Concrete)
```dockerfile
# BAD: layer cache busts on every code change
FROM node:18-alpine
COPY . /app
RUN npm install
RUN npm run build
EXPOSE 3000
CMD ["npm", "start"]
```
Problem: if any file changes, `COPY . /app` invalidates cache, then `npm install` re-runs (slow).

```dockerfile
# GOOD: separate layers, cache npm install
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./           # copy only package.json first
RUN npm ci --only=production    # install (cached until package.json changes)
COPY . .                        # copy source code (cache busts here, but npm install is cached)
RUN npm run build
EXPOSE 3000
CMD ["npm", "start"]
```

**Layer caching rule:** order Dockerfile from **least-changing to most-changing**
- Dependencies (package.json) change rarely → cache is useful
- Source code changes often → put it late so cache isn't wasted

#### Multi-Stage Builds (Why They Matter)
```dockerfile
# Stage 1: build
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build  # compiles TypeScript, bundles, etc.

# Stage 2: runtime
FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
EXPOSE 3000
CMD ["node", "dist/server.js"]
```
**Benefit:** final image has **only runtime files** (no build tools, src files, or dev dependencies)
- Single-stage image: ~500MB (includes TypeScript compiler, dev tools)
- Multi-stage image: ~150MB (only runtime assets)
- Production deployments pull smaller images → faster startup, less disk

**His honest line:**
> "I've used Docker for local development, building images with Dockerfile, and running `docker-compose` locally. I understand layer caching — putting dependency installation before source code so changes don't bust the cache. I haven't built multi-stage Dockerfiles in production, but I understand why: separating build and runtime reduces final image size and removes build tools from production containers."

**Problem:** user opens app, clicks "book property", and backend returns 500. Logs show an error, but which request from which user?

**Solution:** attach a unique ID to every request:


```javascript

});
```

#### Debugging: "It Works on My Machine but Fails in Production"
**Root causes and triage steps:**

1. **Environment mismatch**
   - Local: NODE_ENV=development; Postgres on localhost
   - Prod: NODE_ENV=production; Postgres on remote RDS, different version
   - **Fix:** docker-compose ensures local matches prod; check DATABASE_URL, NODE_ENV

2. **Race condition or concurrency bug**
   - Local: one user; prod: 100 concurrent users
   - Example: two users book same slot simultaneously; locking code fails
   - **Triage:**
     - Correlation ID: find the two requests in logs
     - Metrics: spike in API latency or errors at that moment
     - Database: check transaction isolation level; add row-level locking

3. **Data volume / performance**
   - Local: 100 users; prod: 100k users
   - Example: N+1 query runs fine on 100 users, times out on 100k
   - **Triage:**
     - Logs: look for slow queries (app logs request duration)
     - Database: run EXPLAIN ANALYZE on the slow query; check index usage
     - Metrics: spike in API response time; database CPU at 100%

4. **Secrets / environment variables**
   - Local: DATABASE_URL in .env works fine
   - Prod: DATABASE_URL not set; app crashes silently
   - **Triage:**
     - Check CI/CD pipeline; are secrets injected?
     - App logs: does it log missing env var at startup?
     - Manual: SSH to prod server, run `env | grep DATABASE`

5. **Cache / stale data**
   - Local: no Redis; queries hit database
   - Prod: Redis cache returns stale data
   - **Triage:**
     - Logs: is app hitting Redis or database?
     - Redis: check key TTL, cache hit rate
     - Manual: flush cache, re-test

**His repeatable triage narrative (practice this):**
> "When debugging a production issue, I start by finding the correlation ID from the user's report. Then I search logs for that ID to see the full request flow — which service it hit, what errors occurred. Second, I check metrics: did CPU spike, or latency increase? That tells me if it's a performance issue or an error. Third, if it's a query problem, I run EXPLAIN ANALYZE to check indexes. If it's a concurrency issue, I look at database transaction logs to see if two requests hit the same row. If it's an environment issue, I verify secrets are injected correctly. I don't change code until I know the cause — changes based on guesses make things worse."

## 2. Security, Reliability & Auditability — Why Your ISO 27001 Matters

### The Cash-Handling Difference (vs. Consumer Apps)
- **Consumer apps**: down for 1 hour = users switch to a competitor. Annoying, not catastrophic.
- **Cash-handling apps**: down for 1 hour = a bank can't process deposits, a retail chain can't reconcile cash, an audit trail breaks. **Regulatory & legal consequences**.

### Why This Domain is Different

- **Long-lived hardware**: A cash recycler installed in 2020 might run until 2040. Your mobile app must support backward-compatible device protocols for 20 years. (Contrast: Instagram deprecates APIs every 2 years.)
- **Certificate-based device identity**: Machines in the field use mTLS certificates to identify themselves to your backend. A compromised cert = counterfeit machines can submit false reconciliation data.

### Why Your ISO 27001 Training is Directly Relevant (Frame it This Way)

### What "Certificate-Based Security" Means in Your Context
- **mTLS (mutual TLS)**: Both the machine (device) and your backend authenticate each other using certificates.
  - Device installs a certificate. Your backend validates it. Backend installs a certificate. Device validates it.
  - If an attacker physically swaps a counterfeit machine into a bank teller line, the mTLS handshake fails and the backend rejects it.
  - This is **NOT** OAuth 2.0 (which you know). It's lower-level, infrastructure security.
- **Your honest line**: *"I've implemented OAuth 2.0 social login and JWT-based auth for user sessions. Certificate-based device identity is a different pattern — I haven't built mTLS endpoints yet, but I understand the PKI fundamentals and I'm ready to learn the NestJS patterns for this."*

## 7. Technical Depth: What to Study Before the Interview

### NestJS (2-3 hours)
- **Why**: High probability they'll ask how you'd design a module or controller.
- **Study**:

I'd use a Guard to validate the device certificate on incoming requests, and I'd use an Interceptor to log all telemetry events for audit purposes."*

### AWS Lambda & Serverless (1-2 hours)
- **Why**: JD lists it; they might ask about a use case.
- **Study**:
  - Read: [AWS Lambda — Getting Started](https://docs.aws.amazon.com/lambda/latest/dg/getting-started.html)
  - Key concept: A function that runs in response to an event (HTTP request, SQS message, S3 upload). You only pay for execution time.
  - **Concrete example**: You might use Lambda for: device error alerts (triggered by CloudWatch event → Lambda → send SMS), or one-time reconciliation jobs (scheduled Lambda runs nightly).
  - **Interview Q**: *"When would you use Lambda vs. a traditional NestJS server?"* You: *"Lambda is good for event-driven, short-lived tasks — an alert handler, a batch job. If the service needs to hold state or maintain persistent connections (like WebSocket for live device telemetry), a traditional server is better."*

### OIDC Basics (1 hour)
- **Why**: JD lists it; you need to know it's different from OAuth 2.0.
- **Study**:
  - [OIDC Basics — OpenID.net](https://openid.net/connect/)
  - Key concept: OIDC = OAuth 2.0 + an ID token + a UserInfo endpoint. Used for user identity, not just authorization.
  - **Difference from OAuth 2.0**: OAuth gives you an access token to call APIs. OIDC gives you an ID token with the user's claims (name, email, etc.).
  - **Interview Q**: *"When would you use OIDC instead of OAuth 2.0?"* You: *"OIDC when you need to authenticate a user and get their identity information. OAuth when you just need authorization to call an API on behalf of the user. In a corporate app, if employees log in via OIDC to a central directory (Azure AD, Okta), then use OAuth to grant delegated permissions to backend APIs."*

### mTLS (Certificate-Based Auth) (1-2 hours)
- **Why**: JD lists it; cash-handling devices use certificates.
- **Study**:
  - [Mutual TLS Authentication — Cloudflare](https://www.cloudflare.com/learning/access-management/what-is-mutual-tls/)
  - Key concept: Device certificate validates the device to the backend; backend certificate validates the backend to the device. Both must present valid certificates signed by a trusted CA.
  - **Concrete example**: A cash recycler in a bank has a certificate burned into its firmware. When it boots, it connects to your backend via TLS. Your backend verifies the certificate and rejects the connection if it's fake.
  - **Interview Q**: *"How would you handle certificate rotation on deployed devices?"* You: *"That's a key challenge in hardware. You'd need a process: backend issues a new certificate, device requests it during a scheduled maintenance window or low-traffic period, device installs it, device tests connectivity, device confirms success to backend, old certificate is retired. All with detailed logging for audit."*

## Appendix: Vocabulary & Concepts Crash Course

| Term | What It Means | In This Context |
|---|---|---|
| **mTLS (Mutual TLS)** | Both client and server authenticate each other using certificates. | Device in the field proves it's a real GLORY machine (not counterfeit); backend proves it's the real backend. |
| **OIDC (OpenID Connect)** | A layer on top of OAuth 2.0 that adds identity information. | User logs in to a central directory (e.g., Okta), and your app gets the user's identity claims. |
| **OWASP** | Open Web Application Security Project. A set of application-level security best practices. | Injection, XSS, broken auth, insecure deserialization, etc. |
| **Idempotent** | An operation that produces the same result no matter how many times you run it. | A device handshake is idempotent: reconnect 5 times, the state doesn't duplicate. |
| **Audit log** | A record of every action, who did it, when, and why. Immutable. | If a technician overrides a reconciliation discrepancy, log it: "Tech: John Smith, Time: 2026-09-07 14:30, Override: approved $500 variance, Reason: physical recount." |
| **Non-repudiation** | You can't deny you did something; the log proves it. | A manager approved a cash adjustment. Later they can't claim they didn't — the audit log has their signature. |
| **SQS (AWS Simple Queue Service)** | A message queue. App puts a message in; worker pulls it out later. Decouples producer from consumer. | Device sends telemetry → telemetry goes on SQS → worker processes it later. If worker is overloaded, telemetry waits in the queue. |
| **Circuit breaker** | A pattern where an API returns a safe failure (e.g., "queued, please retry") if the backend is overloaded. Prevents cascading failures. | If database is slow, API says "OK, I've queued your data, come back in 10 seconds." Device doesn't time out. |
| **Eventually consistent** | Data might not be up-to-date immediately, but it will be soon. | A device sends cash count. Backend eventually records it. There's a small delay, but it's guaranteed to arrive. |
| **Strong consistency** | Data is always up-to-date. Reads always see the latest writes. | If a reconciliation is approved, every reader sees it immediately. No delay. |
| **Monolithic architecture** | One big application. All code in one repo, one deploy. | The old way. Backend is one giant app. Hard to scale independently. |
| **Microservices** | Many small applications, each doing one thing well, talking via APIs. | Backend = User Service + Matching Service + Notification Service + Audit Service. Each can scale independently. |
