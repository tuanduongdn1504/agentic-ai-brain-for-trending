The Reordered Eval Set

Pathway published a tool to build a private ARC-AGI benchmark because the public one is contaminated. It is right — and the contamination is one ls away from anyone who looks.

What it is

A 2,139-line Python tool that asks a frontier model — gpt-5.6 by default, any OpenAI-compatible endpoint — to invent ARC-AGI-1-style puzzles, one per API call, so you can score a model on tasks it cannot have memorised. It accompanies BDH-CQ (arXiv:2608.09888, submitted 10 Aug 2026), Pathway's 150M-parameter recurrent-latent-reasoning model, and its press launch.

Each call receives a slot — rows, columns, colour count, pair counts — copied wholesale off one randomly chosen real evaluation task rather than sampled axis by axis, because independent sampling produces, in the code's own words, a 2x2 grid asked to carry 9 distinct colours. Then a convergence loop deduplicates by embedding similarity of model-written rule descriptions, deletes anything too close to a real eval task, validates structure, and regenerates what it removed.

The contamination is worse than the repo says

The premise is that the public eval set appears in web-scraped training corpora — a diffuse claim about the open web. There is a far more concrete channel, and neither the repo nor the paper mentions it. The tool's only open issue, filed by a stranger four days after publication and never answered, claims 375 of the 400 eval tasks sit in ARC-AGI-2's public training split, undetectable by hashing.

I cloned both datasets and tested it at six cumulative levels.

  1. L0same filename / task id376 / 400
  2. L1byte hash of the file0 / 400
  3. L2JSON-canonical hash0 / 400
  4. L3+ demonstration pairs treated as an unordered set375 / 400
  5. L4+ D₄ symmetry, all 8 dihedral transforms375 / 400
  6. L5+ colour permutation371 (4 false negatives, my own tie-break cap)
The mechanism, exactly

Of the 376 shared ids, 375 carry an identical demonstration-pair multiset — same grids, same colours, no rotation, no recolouring — and not one is byte-order identical. In every single case the train pairs are simply in a different order. D₄ and colour permutation contribute zero additional matches. All 375 land on the same task id.

So the issue is right about the number and wrong about the reason. It is not symmetry and not recolouring; it is a shuffle. And because the filenames never changed, it is detectable with ls — the issue's own warning that task-ID matching cannot be relied on is false for this dataset pair.

In fairness to ARC Prize

ARC-AGI-2's readme does say its training set combines tasks from ARC-AGI-1 as well as new tasks. What it never says, anywhere, is that this includes 375 of the 400 ARC-AGI-1 evaluation tasks — in a document whose next line describes an evaluation split as being for models that have never seen these tasks. Disclosed, with the load-bearing half omitted. Controls confirm the method isn't matching everything: ARC-AGI-2's own eval set matches its training set 0 / 120.

The paper's training mixture reaches the same set from a second direction. Section 4.2 names ARC-GEN100K; Google's ARC-GEN repository enumerates 900 task ids, comprising all 400 ARC-AGI-1 training ids plus 328 of the 400 evaluation ids. Whether the specific 100K artifact draws on that subset is not established — but no document in the paper or the repo performs the check, which is precisely what the open issue asks for.

The honest number exists. It is higher. It is in an appendix.

I expected to find that the tool shipped and the trustworthy number did not. That was wrong, and reading the paper corrected it.

It sits in Appendix A.1. The contaminated number is in the abstract, the README, the chart and the press release.

It proves nothing on its own

The gap is equally consistent with the generated set being easier, and nothing in this tool measures difficulty. It matches six surface statistics; grid area and colour count are not cognitive load. The authors say so themselves — not directly comparable — and are right to. Note the direction, though: an ill-posed generated task is one the solver loses, and the repo discloses 19 of 20 hand-checked as solvable, so a ~5% rate means 37.2% understates ability and widens the gap.

The most interesting number is 29.8%. The stratified cohort — deliberately harder, allocated evenly across 16 transformation mechanics instead of following the eval set's skew — lands 0.3 points from the public figure. And that cohort is where the tool earns its existence, in a way its own README never states: the point of a private distribution-matched set is not to restate the aggregate, it is to buy statistical power in cells the real benchmark cannot fill. 400 public tasks cannot support a per-mechanic estimate. 1,131 evenly-allocated ones can, and the answer is a 24× spread — 68.6% on flood fill, 2.9% on gravity and stacking.

"Independent Reproduction" — and none of the three are

The README's last section carries that heading. It credits Łukasz Kaiser, whom Pathway's own blog lists among the company's investors and advisors; then says the results were also independently reproduced by Remigiusz Kinas and Richard Zhong — authors 8 and 9 of the nine-author paper.

Git records the direction of travel. Commit b1ff64c rewrote also reproduced by Richard Zhong into also independently reproduced by Remigiusz Kinas … and Richard Zhong — the word was added, in the same edit that added a co-author. And Pathway's own blog post never uses the word at all, and never mentions Kinas. The independence claim is stronger in the repository than in the press release.

What is not claimed here: that the reproductions did not happen, or that the result is wrong. Kaiser stated publicly that he replicated the ARC-AGI-1 results himself. The finding is narrow: a section headed Independent Reproduction names one investor-advisor and two co-authors, and calls two of them independent.

What the chart admits with a legend glyph

The efficiency-frontier chart marks hollow circles as the public eval set and filled circles as the semi-private set. All three BDH-CQ points are hollow. GPT-5.6 Luna (Low) is filled, at 34.2% for $0.008 — a higher score than BDH-CQ's 29.5%, on the set that is not contaminated. The README states neither the set difference nor that the comparator scores higher; "11× cheaper" is a cost claim, and arithmetically fine.

The footnotes are better than the prose, and two work against Pathway: the $0.0007 is estimated from measured inference compute, assuming USD 3 per H200 GPU-hour, set against competitors' retail API prices; the leaderboard access is dated; and Luna's cost was adjusted down 80% to reflect OpenAI's July price cut, making the comparator look cheaper.

Both halves of the code-versus-prose axis, in one file

The best line in the repository is a comment that describes an enforced information-flow rule: eval descriptions are never placed in a generation prompt — the similarity filter only ever removes; it never instructs. I traced it and it holds: the avoid list draws only from prior generations and prior rejections. One sentence of policy, four lines of enforcement. The .gitignore is a scientific instrument that explains itself, too: publishing the generated tasks puts them into web-scraped corpora and burns them.

Every guarantee protecting the experiment is enforced in code; every guarantee making each task a valid puzzle is a request addressed to a language model. The only evidence for the second column is 19 of 20 hand-checked.

The catch is what the comments hold that the documents do not. 185+88+41+16+8+1+1 = 340: producing 400 novel tasks cost 740 generations, the first-round collision rate at N=400 is 46%, and it has risen at every scale measured. That scaling wall is the most important operational fact about the tool, and it lives in a comment on a backstop constant. Also undocumented: TOLERANCE = 0.40, meaning the distribution check reports PASS at up to a 40% deviation — though in fairness the reported run came in at 1.0%, beating its own gate by roughly forty times.

One real bug

eval_similar_replaced appears exactly three times: initialised at :651, written into sanity_check.json at :862, printed at :882. It is never incremented. The run report's replacements_generated for the contamination filter is structurally always zero — a dead counter in the audit trail of the tool's headline guarantee.

No mint

Declined on five grounds, the decisive one being external prior art: Google's ARC-GEN is an explicitly mimetic ARC generator preserving grid size, colour distribution and pair counts — distribution-matched ARC generation, already published, and named in BDH-CQ's own training mixture. BARC/ARC-Heavy, RE-ARC and ARC-TGI precede it too. Beyond that: technique-not-capability, a research artifact rather than a capability layer, §28 anti-inflation at ~51 standalones, and not the exemplar. Counts stay 46 / 11. It is not an N=2 of the v233 ClawWork row — that is a benchmark harness; this is a dataset generator.

One attribution does not survive checking. The code calls its six categories the six Chollet ARC-AGI categories; Chollet's framework is four Core Knowledge priors, and two of the six have no counterpart in it. The phrase appears seven times across four files — including inside the output JSON's own self-description, so every downstream consumer inherits it. This is the axis the paper's appendix calls confirmatory.

What to take

  • A pre-registered instrument-invalidity guard. Before collecting data, state the condition under which your own measurement axis is not analysable — and make the collector print it. Here: 'other' is the escape hatch; a large share means the closed list is wrong … and should not be analysed as-is, emitted as a warning above 15%.
  • “Only ever removes; it never instructs.” When a filter must consult ground truth, let it delete but never inform — enforced in the data flow, not in a comment.
  • Generate a private set to buy power in the cells your real data cannot fill, not to restate the aggregate.
  • Comment the measurement that set the constant, and the alternative you rejected. Nine here, and the checkable ones reproduce exactly.
  • A .gitignore entry can be a scientific instrument. Write the reason in the file.
  • Test a third party's quantified claim yourself. The issue was right about 375 and wrong about the mechanism, and one afternoon of Node settled both.

Error ledger

Mine, one, self-caught before publication: I framed the headline as the tool shipped, the honest number did not. Reading the paper found Table 6 and inverted it. The error was the vault's signature shape — inferring a mechanism went unused from its absence in the promotional surface.

The fleet's, five, all rejected or corrected. A situating agent built its entire difficulty analysis on Tong et al., arXiv:2405.18742 with quantified human solve rates and a derived calibrated ~24–26%. arXiv:2405.18742 is “Musical Phrase Segmentation via Grammatical Induction.” The paper, its findings and every derived number were invented; all discarded. The same report inverted the arithmetic of unsolvable tasks. The critic's second headline — the paper never mentions arc-task-gen or uses synthetic tasks — is false, and was absence-of-evidence rendered as evidence. The contradiction stage caught four fabricated line citations across three reports, and the critic invented an error in my own grounding.

Method finding, third consecutive ship

Handing each mapper's report to an independent reader as a suspect document, with a mandatory read receipt, caught every fabricated line number — including in the strongest report. It did not catch the fabricated paper, because no agent was asked to treat the situating reports as suspect. The stage only protects the stages it is pointed at. Next refinement: pipeline the contradiction pass over the situating reports too.

Pilot: read and borrow. Do not run it — a 400-task set is ~760 frontier-model calls and the output is ARC puzzles. Risk is genuinely low: no port, no CORS, no exec on model output, egress to exactly two hosts, writes confined to data/. There is simply nothing to gain. Rung 1 is two hours, zero install: read three passages and write the three rules into hireui/evals/METHOD.md.
