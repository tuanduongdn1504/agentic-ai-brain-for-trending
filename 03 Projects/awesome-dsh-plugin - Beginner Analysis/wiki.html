SubjectWhat it actually is

Not a list. A registry with an editorial layer.

The tagline says "a curated list of plugins," and that description is what misleads. Inside is one YAML record per plugin, a compiler that renders those records into two 350 KB bilingual READMEs and a static site, four probes that re-verify the outside world, a weekly decay scan, six CI workflows — and a published machine API.

Public registry API: /plugins.json — deterministic; consumed by the find[er]scripts/build-site.mjs:675

Two independent programs read that endpoint at runtime: dsh-market, an in-harness storefront built by a separate organisation ("This repo is the market app, not the catalog"), and dsh-find-plugin, which registers a find_dsh_plugin tool into the agent so the model searches the catalogue itself.

One ship earlier, v239's community-plugins panel earned a form-factor note describing it as static, index-only, no runtime registry. This is that runtime registry.

FindingThe inventory rule

A submission was merged, and has never appeared anywhere

Every record in data/plugins/ ends in .yml. One does not.

record01Virex__dsh-status-rotator.yml
recordpaicat1__dsh-screenshot.yml
1,388 more
not indexedzmm863-commits__dsh-paperclip

The file is complete and well-formed — url, name, category, and both English and Chinese descriptions. It was reviewed, approved and merged as PR #1192 on 2026-08-17. And entries.mjs:69 reads if (!f.endsWith('.yml')) continue — skipped silently, no warning.

Verified consequences: zero occurrences in either README, zero in the site data, therefore absent from plugins.json, and so absent from the storefront and from the agent's search results. There is even a filename validator that would have caught it — but it sits downstream of the glob that excludes the file.

The rule this teaches. A consistency check between two views of one source cannot see what is missing from the source. Pair every equivalence check with an inventory check that enumerates the input by a different rule than the parser uses.

This is the vault's own condition, precisely: an index-versus-content check between CLAUDE.md and _state/03c would never notice a chapter absent from the index — which is how a file labelled -v183 came to hold entries through v240.

FindingThe doctrine

Automate the evidence. Never automate the irreversible decision.

Three scripts, written by the same hand, all refusing to act on their own conclusions.

Flags — never removes. […] removal stays a human decision because it is irreversible and a scan can be wrong — an outage, a rename, a rate-limit blip. Anything inconclusive is skipped, not flagged: a decay report must only ever contain evidence, not doubt.scripts/scan-decay.mjs

The bleed detector — which finds one entry's description leaking into another's, after that happened twice while every existing check passed — is likewise "reported, not enforced," on a threshold calibrated by running it: at 40 shared characters, a full pass over ~1,170 entries surfaced five pairs, all genuine. The site builder carries a publish-time plausibility floor added the day a bad probe shipped 1,362 null star counts to everything downstream.

The sharpest contrast of the run, one ship apart. v239's pr-review.mjs auto-closed a substantive bug report for template non-compliance. v240 refuses to auto-remove a single entry.

Every non-obvious constant here carries a comment naming the incident that motivated it and the measurement that calibrated it. That habit is the exact inverse of the vault's — accreting claims without provenance, which is why its rows cannot be retired.

FindingPropagation

A contested claim, caught moving downstream again

The editorial policy requires a reviewer to check whether the code does what the entry claims, "including any numbers or API names." The catalogue's verified entry for the v239 subject reads: "…pet, live token stats, and a skin center."

That is the feature v239 flagged as advertised but absent. Rather than lean on the prior ship, the live source was re-checked here: the current 33,162-byte README contains zero occurrences of token or usage. Its single Chinese "token" is on line 81, in the mobile-pairing section — the pairing token, not usage statistics.

v239 republished upstream's retracted benchmark into its npm description. v240 republishes v239's unsubstantiated feature into its registry API. The same failure mode, pointing the other way, one ship apart — a claim travelling downstream through a live dependency graph faster than anyone re-checks it. The mechanism is banal, not malicious: the line was copied from the plugin's own tagline, which is precisely what the policy warns against.

SecurityOne good, one honest

The best CI artifact of the run — and a limit the project discloses itself

a token is in scope here, so nothing from the pull request is ever executed. […] Checking out refs/pull/N/merge and running npm ci there would hand the token to fork-supplied install scripts, which is the pull_request_target footgun this workflow exists to avoid..github/workflows/pr-gate.yml

All six workflows run contents: read; no lifecycle scripts; two current dependencies. The fork-triggered job holds no token, and the privileged job treats pull-request content strictly as data in a scratch directory.

Against that, the README's boast — "if a description claims '46 tools', someone counts them" — has no mechanism behind it. The contributing guide says so before anyone else can: "A green CI run is the precondition, not the decision… It cannot tell whether a plugin does what its entry says." Nothing listed is security-scanned; the tarball probe only confirms a URL resolves.

Two cautions. A listing is not a safety signal, and the project says so above 1,390 install commands. And the committed lockfile resolves two of three packages from a mirror registry while npm ci runs in four workflows — integrity-hashed, so the exposure is availability and install-traffic visibility, not integrity.

PatternNo mint

Declined, on prior art that was verified rather than assumed

The candidate row — a curated catalogue publishing a runtime-consumed registry API — is real but not new. awesome-selfhosted already splits into a per-entry-YAML data repository that generates both README and website; HACS is already a curated community registry consumed at runtime by an in-app storefront in the host application. An independent adversarial check returned: "a well-executed curated list with good engineering, but it is not a structural innovation." The genuinely newest element — the agent-callable tool — lives in a separate repository. Recorded as a deferred watch axis at N=1.

Also declined: a tempting revival

skills-lock.json pins two corpus subjects by content hash — v85 and v51 — the same filename and purpose as a pattern the corpus retired 225 wikis ago for lack of a second instance. It does not qualify: this is not a framework, and the manifest is not load-bearing (nothing verifies the hashes or consumes the skills). An initial over-reading, reversed by the verifier.

And a note the corpus owes itself

v237's verdict had already named this repository — "Ecosystem-formation data-point, not a subject." That call was made on the genre label without reading the source, and was wrong on the facts. The lesson is about intake, not this repo: do not settle a subject question on form-factor alone when the form factor is cheap to verify.
